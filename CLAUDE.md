# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

## What this is

`vid-fp` — a Linux CLI that finds duplicate videos and clips by perceptually fingerprinting their keyframes. Binary-only crate (`[[bin]]`, no `lib.rs`); the README is the user-facing spec and the man page is generated from the clap `Args` doc comments.

## Build and test

A plain build links the system's **shared** FFmpeg. On Debian/Ubuntu: `libavcodec-dev libavformat-dev libavutil-dev libswscale-dev clang pkg-config` — only those four libav\* libraries, since `ffmpeg-next` is pinned with `default-features = false` (avdevice and avfilter are unused and were dragging libavc1394 and libncursesw into `DT_NEEDED`).

`ffmpeg-next` is pinned to **8.1**, and that is deliberately newer than any FFmpeg you are likely to have. Only the crate's *forward* compatibility is broken: 8.1 compiles and runs correctly against FFmpeg 6, 7 and 8 headers because `ffmpeg-sys-next` detects the version and gates the wrapper on cfgs, whereas the 6.x crate fails against FFmpeg 7 headers with ~30 errors inside the dependency. Pinning the newest widens the host range; do not lower it to match what the release vendors.

The **released** binary is different: it statically links a vendored FFmpeg 8 + dav1d, so it needs no FFmpeg at all at runtime.

```bash
./scripts/build-ffmpeg-static.sh   # ~10 min, once; -> ./ffmpeg-static (gitignored)

cargo build --release --features static-ffmpeg              # what ships
cargo test  --release --features static-ffmpeg -- --nocapture
```

`build.rs` defaults to `./ffmpeg-static`, so no env var is needed day to day; `FFMPEG_DIR` overrides it for CI and for anyone relinking. **Do not export `FFMPEG_DIR` from a shell profile** — `ffmpeg-sys-next` reads it whether or not the feature is on, so a plain `cargo build` would then try to link the static archives and fail at `ld`.

**Pass `--features static-ffmpeg` to `cargo test` as well as `cargo build`.** `cargo test` builds the bin target too, so a bare `cargo test --release` silently overwrites `target/release/vid-fp` with a *dynamic* binary and then measures it against the static baselines — which shows up as a `4-20` failure reading 75/186 that looks exactly like a real regression. The harness prints a warning when it detects this, but the warning is easy to scroll past.

**Accuracy numbers only mean something from the static build**, because the golden CSVs were taken with it — see the accuracy-test note below.

```bash
cargo build --release --locked     # release profile: lto + codegen-units=1; use it for any timing
cargo clippy --all-targets
cargo test                          # unit tests (in-file `mod tests`) + the accuracy integration test
cargo test --bin vid-fp share_for   # single unit test — tests live in the binary, so --bin, not --lib
cargo test --test local_accuracy_test -- --nocapture
```

`tests/local_accuracy_test.rs` is a machine-local regression harness: it shells out to `./target/release/vid-fp` against `/home/daniel/Documents/AN` with a ladder of `-d`/`-p` settings and asserts exact group/file counts against baseline CSVs stored in that folder. It **returns early and passes** when the directory is absent, so a green `cargo test` on another machine proves nothing about accuracy. Build release first — it runs the binary, not the crate.

**Build it with `--features static-ffmpeg` before trusting the result.** The baselines were re-taken against the vendored FFmpeg 8, and the `4-20` profile is genuinely FFmpeg-version-sensitive: a dynamic build against FFmpeg 6 reports 75/186 there where the static one reports 74/184, because one pair's coverage falls by a single 0.5 s hash sample and drops under the 20% gate. The other two profiles agree across both. That profile has always sat within a percent or two of its gate — it is the same one that moved for the PTS→DTS fix — so treat a lone `4-20` diff as a question about which FFmpeg produced it before treating it as a regression.

`src/fingerprint.rs` tests decode `tests/fixtures/test_video.mp4`, so unit tests need a working FFmpeg at runtime too.

## Pipeline

`main::run` drives one linear pass; every stage polls `utils::shutdown_requested()` and returns `Outcome::Interrupted` rather than unwinding.

1. **`sources::collect`** — walks folders / reads stdin or `--from-file`, stats each file exactly **once**, and deduplicates on `(device, inode)` so symlinks, hard links and overlapping scan roots collapse to one entry. Everything downstream (cache stamp, sort, thread weights, prune) reads the `ScannedFile` fields; nothing re-stats. What comes back is a `Library`: those files, plus the walked folders and resolved excludes the `--move-to` loop guard needs — see that invariant below.
2. **Cache pass** — files are sorted largest-first, then *every* cache lookup happens before *any* decode. This split is deliberate: interleaving them under rayon let one slow decode block cached neighbours in the same work slice.
3. **Weighing pass (`fingerprint::weigh_decode`)** — every cache *miss* is opened once, header only, and asked how much decoding it implies; `todo` is then re-sorted on that. Like the cache pass it is complete before any decode starts, because the thread budget and the progress bar are both apportioned against the total.
4. **`fingerprint::fingerprint_video`** — decodes keyframes only, box-filters each to 16×16, DCT-transforms, and keeps the 8×8 low-frequency corner as a 64-bit hash (exactly 32 bits set, hence only even `-d` values are meaningful). Featureless frames (black, fades, title cards) are dropped below `MIN_AC_ENERGY` so they can't link unrelated files. Sample times are **milliseconds of decode time anchored at the first keyframe**, not PTS — MP4 `ctts` skews PTS once non-key packets are discarded.
5. **`compare::find_all_matches`** — two phases. Phase 1 builds a `BlockIndex` over each of 4 16-bit hash blocks and proposes candidate pairs; the probe radius is `Tolerance::widest() / 4` with nothing capping it, so it is exhaustive at every tolerance, and `index_is_cheaper` skips the index entirely (comparing every pair outright) once the probe grows wider than the library. Phase 2 compares every proposed pair exactly, against **two** tolerances rather than one — see the corroboration invariant below. Coverage is **directional and measured in milliseconds of runtime**, not in frame counts — a hash stands for the span until the next sample, so two encodes sampling at different rates still agree on how much footage overlaps. Phase 2 runs under a progress bar (`verification_bar`), because at a loose `-d` it is minutes of silence after phase 1's one-line "verifying..."; workers batch their reports through `Ticker` for the same reason the decode stage has `PROGRESS_STEP_BYTES`.
6. **`clustering::find_duplicate_groups`** — maximal cliques via Bron-Kerbosch with Tomita pivoting, run **per connected component** and under a ceiling. A group asserts "every one of these matched every other", which is what lets `export.rs` rank them against each other. Adds no thresholds of its own — the ceiling is not one; it is a refusal to answer, and it is counted as a problem. Groups therefore **overlap**: a file can be reported in several, and the report is a list of relationships rather than a partition of the library.
7. **`export::output_results`** — ranks inside each group but resolves each file's label ONCE across all of them (REVIEW > DELETE > KEEP), performs the disposal, and returns the paths that moved so `main` can drop their cache entries.

`utils` holds the ranking rules (`GroupMaxima`, `find_best`), formatting, and the shutdown flag. `stats::RunStats` tallies **skips** (intentional: `--min-duration`, excludes, inode aliases) separately from **problems** (the run did less than asked) — only problems set exit code 2.

**`--from-report` is a second entry point that skips all of it.** `run` branches to `main::run_from_report` before anything touches the filesystem; `report::apply` reads a report an earlier run wrote, takes the rows whose `action` says `DELETE`, and disposes of exactly those. It shares four things with the grouped path and nothing else: `confirm::approve`, `export::dispose_one`, `export::disposed_line`/`trouble_lines`, and `cache_forget`. It works because the destructive step only ever consults a path and a size, and both are report fields — see the `dispose_one` invariant below.

**Both formats that record a size are readable, and only the extraction is per-format.** `report::read` dispatches on the file's first non-whitespace byte (`looks_like_json`): `{` or `[` goes to `read_json`, everything else to `read_csv`. It used to dispatch on the extension, which worked only for as long as the writer did too — `--format` made `-o dupes.bak --format json` writable, and that report would have gone to the CSV reader and been refused for want of columns it was never going to have. The sniff is also what gives a JSON array named `.csv` the complaint about its missing `results` key rather than one about a missing column. What is NOT duplicated is the judgement — a format reader pulls three cells out of one row and says where that row was, and every question about what those cells mean is answered once in `Rows::consider`, for rows of every format. That is the whole answer to the objection the module doc used to carry, that a second parser would be a second place to be wrong: it is, only if it is allowed to decide something. `test_every_report_format_that_records_a_size_can_be_handed_straight_back` (in `export.rs`, where the writer lives) runs a real report through each format and back. The JSON's rows are the `results[].files[]` objects; the `matches` array nested under each carries a `full_path` too and is deliberately never read, because it names the file that row was measured *against* — the one that WON. `.txt` stays unreadable, and that is a property of the format: it records no size, so there is nothing to check a file against before removing it.

## Invariants worth knowing before you change things

**`-d` is two thresholds, and the second one needs a witness.** `Tolerance::for_distance` turns the flag into `strict = -d` and `loose = -d + 1.5 sigma` (6 bits on a 64-bit hash). A frame match inside `strict` is taken outright — so `-d` keeps the meaning it had before corroboration existed — and one between `strict` and `loose` is taken only if a *different* frame of each video also matches within `ALIGNMENT_TOLERANCE_MS=500` of the same time offset (`compare::corroborated`). Both halves move with every rung and **neither is clamped against a constant**, which is what keeps the flag a sensitivity control; `test_the_tolerance_pair_moves_monotonically_with_the_flag` pins the monotonicity the docs promise.

**Every threshold here is stated in sigma, not in bits, and that is load-bearing.** The distance between two unrelated hashes is Binomial(`HASH_BITS`, ½): mean 32, sd `sqrt(HASH_BITS)/2` = 4 for this hash. `sigma()` and `sigma_below_chance()` are what turn "1.5 sigma" into 6 bits and "5 sigma below chance" into 12. A bit count means nothing without the width it came from — widen the hash and a hard-coded 12 silently becomes a *tighter* rule, where 5 sigma stays 5 sigma. This replaced an earlier pair of fitted constants (`UNCORROBORATED_BITS = 8`, `CORROBORATED_BITS = 12`) that clamped both sides; see the design note below for why they had to go.

The measurement that justifies corroboration at all, taken over `benchmark/labels.csv`: among pairs the human labeled SAME, sample pairs landing within 0.25 s of each other are within 4 bits 64% of the time and within 12 bits 75%; among pairs labeled DIFFERENT the same temporally-coincident sample pairs are within 4 bits **0.0%** of the time and within 12 bits 0.6%. Distance alone cannot separate those two populations — 152 of the 181 SAME pairs the old code missed at `-d 4` had no frame pair within 4 bits at all, while their best frames sat at 6-12. Distance *plus* agreement about when is what separates them.

**How many witnesses is set by how often chance produces a match that close, not by a constant.** `witness_schedule` reads `chance_orders_of_magnitude(x)` — `-log10 P(two unrelated hashes land within x bits)`, the Binomial tail — and asks the cluster (the match plus its witnesses) to carry `CORROBORATION_BUDGET = 2` times what one match at `EVIDENCE_ANCHOR_SIGMA = 5` sigma below chance carries. That is 1 witness out to 12 bits, 2 at 14, 3 at 16, 4 at 20. The budget and the anchor are **one calibration between them**, not two: 2 is the value that puts the anchor at exactly one witness, and `test_one_witness_is_exactly_enough_at_the_anchor` fails if they drift apart. The independence the arithmetic assumes is not real — near-static footage produces matches that corroborate each other for nothing, which is why a witness must be a different sample on *both* sides — so only the SHAPE comes from the tail.

**Measured, links scored against the hand-labeled pairs.** Every rung beats the flat single threshold it replaced (`F1`, SAME): `-d 0` 0.406 -> 0.715, `-d 2` 0.684 -> 0.791, `-d 4` 0.762 -> **0.859**, `-d 6` 0.827 -> 0.909, `-d 8` 0.887 -> 0.931, `-d 10` 0.918 -> 0.939, `-d 12` 0.914 -> 0.915. Precision at the default is 99.7% (one false positive), and the ladder walks it down smoothly: 99.2, 98.3, 96.0, 88.5. The honest way to read the gain is at MATCHED precision, which does not depend on where this corpus's knee sits: at ~99.5% precision the flat rule reached 79.8% recall and this reaches 86.0%; at ~97%, 86.4% against 91.1%; at ~91%, 92.1% against 93.4%. The curve moved, not the operating point.

The cost is 0.13 s of warm comparison time on the 756-file corpus (0.07 -> 0.20 s, against 175 s of decode) and nothing measurable in peak RSS (522-524 MB either way, inside the run-to-run spread); the fingerprints are untouched, so **this needed no `CACHE_TABLE` rename and no re-decode**. Cold wall time is 175.3 s for the old binary and 174.9/175.3 s for the new one across an interleaved batch — the same, and the reason the batch has four runs is the documented first-run effect (153.8 s, whichever binary goes first).

**Why the clamped version was abandoned, so it does not come back.** The first version of this rule was `strict = min(d, 8)`, `loose = max(d, min(d + 8, 12))`. It scored better on this corpus at the loose end — 99.3% precision at `-d 12` against 88.5% — and it was still wrong, for a reason no accuracy number shows: `loose` reached its ceiling at `-d 4`, so `-d 4, 6, 8, 10, 12` differed only in the lone-match side and produced 470, 479, 490, 490, 490 pairs. Five rungs of a sensitivity knob doing nothing, with the flat stretch positioned by whichever corpus the two constants were fitted to. **A knob whose range is fitted to one library does not generalise, however well it scores on that library.** If you are tempted to add a ceiling back, the thing to check is not F1 — it is whether every rung still moves.

Measured alternatives, so they need not be re-derived (all at `-p 20`, scored on the same labels): `strict = -d - 2, loose = -d + 2` scores *worse than a flat threshold* below `-d 10` (0.744 against 0.762 at `-d 4`) because the lone matches it gives up cost more than a narrow corroborated window wins back; `loose = -d + 8` buys recall at the default (0.903) and gives it back from `-d 10` up, where the strict side is what starts admitting false positives; removing the schedule and letting any cluster size pay for any distance collapses to 83.9% precision at `-d 2`, because that is where the independence assumption fails hardest.

Three consequences worth knowing before you touch it:

- **Phase 1 must probe at `loose`, not at `-d`.** A pair whose only matches are corroborated ones is never proposed otherwise, and the rule would be unreachable exactly where it earns the most. At the default this makes the probe radius 2 instead of 1.
- **Every frame match is judged on its own distance**, so one pair can be admitted on a mixture — a 4-bit match taken outright, a 10-bit one with a witness, a 16-bit one with three. There is no per-pair notion of "how good the match was" anywhere in `match_overlap`, and the coverage figures the report prints cannot tell you which kind carried a pair.
- **A file with one sample can never be corroborated**, because a witness must be a different sample on *both* sides. This closed the bad DELETE in [[single-keyframe-files-defeat-match-percent]]: at `-d 10 -p 90` the `leg raises_18`/`_19` pair, which used to be admitted on `_19`'s lone hash reading 100% covered, is gone, and the genuine `_8`/`_10`/`_11`/`_15` cluster still stands.

**One run per cache, and `--cache` is the only way around it.** redb takes an exclusive `flock` when the database is opened, and the handle lives for the whole of `main`, so the lock covers the entire scan rather than the cache pass — a second concurrent run cannot be made to share it by any amount of retrying, which is why there is no wait-and-retry flag. `resolve_cache_path` picks the file (XDG default, or `--cache`, which accepts a directory and puts `CACHE_FILE_NAME` inside it) and `open_cache` is the only place that opens it. That function matches `DatabaseError` rather than wrapping it, because contention, a format upgrade and a permissions problem want three different sentences and the single `.context()` this replaced gave all four failures one sentence with no path in it. The legacy sled sweep stays on the default location only; superseded-table retirement applies to any cache, since a user's own cache file goes stale the same way.

**`--from-report` is the one mode that runs without a cache, and only a locked one.** It reads nothing out of the cache — the single call is `cache_forget` after disposal — so refusing to replay a report the user has already reviewed would block a deletion for as long as some unrelated scan takes. Worse, the advice the locked message gives would be wrong there: a cache handed over with `--cache` is not the one holding those entries, so the run would delete the files and purge nothing, silently. `main` therefore degrades to `db: None` on `CacheUnavailable::locked` alone, and only for that mode; `run` and `run_from_report` take `Option<&Database>`. The purge is given up loudly — a warning before the confirmation prompt, `cache_purge_failed` in the problem summary, exit 2, `--prune-cache` collects the entries later. `--clear-cache` is exempt, because emptying a cache is the thing that was asked for rather than bookkeeping. Every other open failure is still fatal in every mode, which is what `locked` exists to distinguish.

**Cache correctness is enforced by the table name.** `CACHE_TABLE` in `main.rs` is currently `fingerprints_dct_ct_ff8_tail`; `SUPERSEDED_TABLES` lists the dead ones, dropped whole on first run. Appending a field to the end of `VideoFingerprint` is self-invalidating — old entries run out of bytes and bincode fails cleanly. **Changing what an existing field *means* (units, clock, hash algorithm) is not caught by anything**, so it requires renaming `CACHE_TABLE` and pushing the old name into `SUPERSEDED_TABLES`. Read the comment above those constants; each past rename records the bug that forced it.

The `_tail` suffix is the most recent rename, and it is the cheapest kind: `sample_times` divided the span of a video by its sample *count* rather than by the number of gaps between the samples when extending the last sample, so `total_ms` came out a few tenths of a percent short. Same field, same units, different value — which is exactly what a layout check cannot see. It fires whenever the samples outrun the runtime the container reported, not merely when there is no runtime at all (an MP4 opening on a negative dts gets there, because anchoring at the first keyframe shifts every sample later); three of the 727 files in the local corpus hit it. No grouping decision moved on any of the three accuracy profiles, so that rename cost a re-decode and nothing else.

**The vendored FFmpeg version is one of those meanings.** The `_ff8` suffix names the rename before that: decoder output is not bit-identical across FFmpeg majors, and the `Stamp` records mtime, size and the sampling knobs but deliberately *not* an FFmpeg version — so entries written either side of a version change are indistinguishable to a lookup. Bumping `FFMPEG_VERSION` in `scripts/build-ffmpeg-static.sh` across a major therefore costs a `CACHE_TABLE` rename and a re-taken accuracy baseline, exactly like changing the hash algorithm would. It is not a routine dependency bump.

**What belongs in the cache `Stamp`.** mtime (with nsec), size, and the sampling knobs (`--keyframe-interval`, `--min-keyframes`) — anything that changes *which frames get hashed*. Thread count is excluded on purpose (it changes only speed); the claim that it changes nothing else is checked by `test_threaded_decode_is_bit_identical` and holds over the whole corpus. `-d`, `-p` and `--min-duration` are comparison-time and must never enter the stamp.

`Stamp::matches` compares `min_kf_samples` only when `sampling_is_on(kf_interval)`, because that flag is a *floor on the interval* and with no interval there is nothing to floor — see `effective_interval`, which will not read it either. It is still written into every stamp, so the struct layout (and therefore the byte offset the fingerprint begins at) is unchanged and existing caches keep hitting.

**`--min-keyframes` is not monotone, and its default of 12 was measured rather than guessed.** Coverage is the span each hash stands for, so a denser sample makes every hash stand for less; extra samples that match nothing dilute a pair's coverage percentage and can push it back under `-p`, taking a pair OUT of the report. This is not a small effect and it is not noise: swept over `--keyframe-interval` 5/13/21/29 at the default `-d 4 -p 20`, F1 on the labeled pairs peaks at `-m` 4, 12, 20 and 28 and collapses at 8 and 16 (AN 0.791 at 6 → 0.744 at 8; Wire 0.829 → 0.526). Re-running the dip at `-p 0` proves the mechanism: on Wire at `-i 21`, **all 64** of the pairs `-m 8` loses are found with the gate off, and there the two settings are identical (406 pairs, same P and R). The old default of 4 sat on a safe rung but left a lot behind — 12 takes combined F1 across the two corpora from 0.847 to 0.918 for 9.4% more wall time, and it is the best rung on the long-video corpus outright.

The reason it is that cheap is that `effective_interval` is `min(kf_interval, duration / min_kf_samples)`, so the floor only reaches a file whose runtime is under `kf_interval × min_kf_samples`. A 59-minute episode is sampled at the flat interval whatever this flag says: over the whole `-m` 1→28 range the Wire folder moves 22.2 s → 23.7 s, against 25.8 s → 37.4 s on the short-clip corpus. Anyone re-tuning this must say which `-p` they measured at, because the flag's whole shape comes from that interaction. The harness is `benchmark/kf_sweep.py` and `benchmark/kf_report.py` (the latter takes `--only-under` to score a subfolder scan against just the labels it could reach).

**Decoder threads are apportioned by measured decode cost, not by file count and no longer by bytes** (`share_for`, `ThreadBudget`). FFmpeg fixes a decoder's thread count when it is opened, so a heavyweight must be given its share at the moment it starts or never — hence the heaviest-first sort, the atomic cursor instead of rayon (rayon's splitting breaks that ordering), and the blocking `claim`. A `Grant` releases its threads on drop, including on error and Ctrl-C.

**The weight itself comes from `fingerprint::weigh_decode`, and the unit is keyframe-pixels.** ~93% of fingerprinting time is intra decode of the keyframes, so the honest weight is how many of them there are times how big they are; the file's size only tracks that through bitrate, which is why a well-compressed 4K file used to be scheduled behind a bloated SD one. The keyframe count is not estimated — it is counted out of the container's own index, which MP4 and AVI build while reading the header and which Matroska will build if you ask it for a seek (80–250 µs; the count equalled the keyframes actually decoded on all 753 files measured). Measured against single-threaded decode time on the files big enough to time, that halves the median error against the old byte weight (21% vs 46%) and cuts the 10th-to-90th-percentile spread from 5.5× to 2.2×. Everything after that is a ladder of fallbacks — assumed 4 s keyframe spacing when there is no index, then `WORK_PER_BYTE` when the file will not open at all — because a file that cannot be weighed still has to be scheduled, and the decode is where a broken one gets reported.

The cost of it is one `avformat_open_input` per file, **paid only on cache misses**: the weighing pass sits after the cache pass, so a re-run over a warm cache pays nothing. That placement is also why `sources::collect`'s size sort is now only an approximation of the real order — `todo` is re-sorted on the measured weight once the pass has run.

**Memory is deliberately flat across a run.** Frames live in one contiguous `FRAME_STRIDE`-sized allocation per video so glibc serves it via mmap and returns it at once; `main()` pins the mmap/trim thresholds with `mallopt` to stop dynamic growth undoing that. Don't replace the frame buffer with a `Vec<Vec<u8>>`.

**DELETE always rests on a direct measurement, and the clique rule is what enforces it.** A file marked DELETE lost the ranking inside a group whose members were all compared with each other, so it was compared with the file that beat it. Nothing in `export.rs` re-checks this — it does not have to, and the guard it used to carry (`matches.coverage(idx, s).is_some()`, plus a `--trust-chains` flag to switch it off) was removed when grouping went back to cliques, because a complete subgraph makes it unfalsifiable. **Loosen the clustering rule and that guard has to come back with it.**

**Clique enumeration is bounded per component, and a component that outruns its bounds is dropped whole.** Maximal-clique enumeration is 3^(n/3) in the worst case and the worst case is reachable from the command line — unrelated hashes sit ~32 bits apart, so a loose `-d` over a large library is a near-complete graph by construction. Measured on the 756-file local corpus, groups by `-d`: 141 at 8, 232 at 12, 574 at 14, 1,891 at 16, **9,003 at 18, 139,025 at 20** (52 s, 1.4 GB RSS, a 2.6-million-row CSV), and at `-d 22` the old build was still going after 5 minutes capped at 1.5 GB. That is the hang, and it is two rungs past a setting that still works.

Two ceilings stop it, both per connected component and both in `Ceilings`: `SEARCH_BUDGET_PER_COMPONENT` (50M set probes, charged per recursion step by `step_cost`) and `MAX_GROUPS_PER_COMPONENT` (100k cliques). The budget is one number covering three failure modes: a probe is a hash lookup, so time is counted directly; the sets a step holds are never larger than the work it does on them, so the heap follows; and depth follows too, because a clique of `d` members costs ~`d^3 / 3` probes, which caps recursion at ~530 frames. Where exactly the group ceiling sits barely matters — this corpus goes 9k → 139k → uncountable across two rungs of `-d`, so anything from 20k to 200k cuts in the same place. Results are **byte-identical to the pre-ceiling build at `-d 4, 8, 12, 14, 16, 18`**, and it bails in 1-7 s from `-d 20` up.

**`step_cost` charges the pivot walk, not the size of the sets, and that distinction is the whole ceiling.** `HashSet::intersection` walks the smaller side, so pivot selection costs `sum over p ∪ x of min(deg(v), |p|)` — quadratic on a dense component, linear on a sparse one. The first version of this charged `|p| + |x|` and undercounted a dense component by a factor of `|p|`; the case that exposed it was a *nearly complete* graph, which has few enough maximal cliques to slip under the group ceiling while every step carries hundreds of thousands of probes. `-d 40` on the local corpus ran **eleven minutes single-threaded, still climbing, with neither ceiling firing** — the exact failure the ceilings existed to prevent, one rung outside where they were tested. Do not replace this with a flat per-step charge: it has to stay proportional to the work, or it stops bounding anything on the graphs that matter. Measured probes for the largest component: 5.4k at `-d 4`, 5.6k at `-d 12`, 75k at `-d 16`, 1.03M at `-d 18` (a 48x margin under the budget), 11.2M at `-d 20` where the group ceiling fires first, and the full 50M at `-d 32`, where the graph is complete enough that not one clique finishes.

**`-d` stops at chance (`compare::max_hamming_distance()` = 32), not at the width of the hash.** Two unrelated frames sit 32 bits apart on average, so at 32 half of all unrelated frame pairs already match and the flag has nothing left to control; above it the library is one group and, with `--delete` armed, one survivor. The old bound was 64 — refusing only the arithmetic that could not mean anything, and admitting a whole range that could not mean anything either. It is also the range where the clustering ceilings stop being enough on their own (the `-d 40` case above), so the cap and `step_cost` are two independent answers to the same class of input; both are worth having, because the cap is about what the flag means and the budget is about what any input can cost. Stated as `sigma_below_chance(0.0)` for the same reason every other threshold here is in sigma.

Three properties worth keeping if you touch this. **Per component**, so one dense folder does not cost the user the groups in every other folder — a maximal clique never spans components, so this changes no result. **Dropped whole**, never partially: which cliques a truncated search found depends on `HashSet` iteration order, so reporting them would make the same library group differently run to run, and `--delete` would act on half a component's relationships. **Counted as a problem** (`stats.clustering_abandoned`), so the run exits 2 and names the files — this is the one case where raising `-d` takes files OUT of the report, which the README's monotonicity claim now says out loud. The recursion also polls `shutdown_requested()` on every step, which is what makes the "every stage polls it" claim above true; that path is deliberately not unit-tested, because the flag is process-global with no reset and setting it would leak into every test running beside it.

**`-t` is bounded by MEMORY, not by CPU time, and that is not what the flag looks like it controls.** Peak RSS is close to linear in `--threads` while throughput is flat. Measured with a fresh cache each run, so every file decodes — 100 720p clips: 5.2-5.4 s at every rung, 112 MB at `-t 8`, 205 at 16, 370 at 32, 620 at 64. 16 1080p clips: 5.2-5.5 s at every rung, 422 MB at 8, 647 at 16, 1,137 at 32, 2,022 at 64. That is ~9 MB per extra thread at 720p and ~28 MB at 1080p, so the slope is a property of the **library**, not of the machine, and 4K footage costs roughly four times the 1080p figure again. CPU utilisation is already 71-73% of eight cores at `-t 8`, which is why nothing above one worker per core buys wall time on local storage. Note the 1080p column keeps climbing past `-t 32` although 16 files cap the *worker* count at 16: the budget is what widens, so each decode is handed more decoder threads and each of those holds its own frame buffer. Both mechanisms scale with this one number, and it is the figure the `mallopt` calls and the single contiguous frame buffer exist to keep flat — an unbounded `-t` is the one input that undoes all of that.

**Thread creation is the cruder limit and bites two orders of magnitude later.** Timed on a warm two-file cache, so the pool is the whole cost: 0.02 s from `-t 8` through 256, 0.10 s at 512, 0.58 s at 1,024, 2.0 s at 2,048, 5.3 s at 4,096, 14.0 s at 8,192, and at 16,384 it burns 63 s of wall and 459 s of user time before failing. That is the reported bug — `-t 1000` spending 19.7 s on a two-file library, `-t 20000` failing inside rayon's `build_global` with EAGAIN against this machine's `RLIMIT_NPROC` of 22,609 and then surviving a first SIGTERM.

**So `MAX_THREAD_OVERSUBSCRIPTION = 4` sits in a wide gap rather than on a tuned point**, and the gap is left wide on purpose: the case that justifies any oversubscription at all is the one that cannot be measured here — videos on a network mount or a slow disk, where workers block on I/O and cores idle. A ceiling tuned to local decode would say 1 and refuse it. `MIN_THREAD_CEILING = 16` is a portability floor for the same reason, and does nothing at 4 cores or more: on a one-core VM the useful worker count is set by the storage's latency and has nothing to do with the CPU, where 4x would land at 4. Per core rather than flat so it travels — a flat 32 is a hard cap on a 128-core machine and 16x oversubscription on a dual-core one — and per core also tracks the memory, since the machines with many cores are the ones with the RAM for many frame buffers.

**It is bounded in `main` rather than in `run`, and clamped rather than refused.** Early because rayon's `build_global` allocates the whole pool eagerly, so an absurd value is already spent by the time `run` — where every other numeric flag is validated — is reached. Clamped because `-d`, `-p` and `--min-duration` change what the run *reports* while a thread count changes only how fast the same answer arrives, which is the same claim that keeps the count out of the cache `Stamp` and that `test_threaded_decode_is_bit_identical` holds up over the whole corpus. `active_threads` is the clamped figure everywhere after that — the rayon pool, `ThreadBudget`, the worker count and the `Settings ->` line all read it — so nothing downstream ever sees the number the user typed, and the clamp is said out loud (`log::warn!`, named in terms of memory) rather than applied silently.

**Labels are resolved globally, not per group** (`export.rs` pass 1). Precedence is REVIEW > DELETE > KEEP: a file marked DELETE in any group reads DELETE in every group it appears in — including one where it won the ranking — and a file held for REVIEW anywhere is held everywhere. The consequence is that deletions chain: B loses to A in one group, C loses to B in another, and a single pass removes both while A survives, though C was never measured against A. Each hop is a direct measurement; the end-to-end conclusion is their sum. That is deliberate — it is what stops a chain needing one re-run per hop — and it is why a group can end with no survivor at all (7 of the 129 groups a default scan of the local corpus produces, holding 19 files; every one of them traces to a survivor in another group, verified against `benchmark/labels.csv`, and three — `barbell biceps curl_{36,38,39}` — take two hops to get there rather than one).

Bit-derived metrics (quality, size) are compared **only within a codec** — a mixed-codec group ends with one survivor per codec, all flagged REVIEW. Both rules are load-bearing safety properties described in the README's Safety section.

**The `-p` gate reads `max(coverage_a, coverage_b)`, and the DELETE rule deliberately does not re-read it.** This is by design, not an oversight, and it is what makes clip detection work: a two-minute clip cut from a twenty-two minute episode covers ~100% of the clip and ~9% of the episode, so only the clip's side can ever clear a threshold. The pair is admitted if *either* file is sufficiently covered, and `export.rs` then asks only whether a measurement exists for the pair (`matches.coverage(idx, s).is_some()`), never how large it was.

**Zero coverage is refused separately from the gate, because `-p 0` cannot refuse it.** `measure_pair` tests `pct_a.max(pct_b) <= 0.0` before it tests the floor. Without that, `-p 0` made `< min_match_percent` false for every pair phase 2 was handed, and on the direct route phase 2 is handed *every pair in the library*: `-d 4 -p 0` over 110 unrelated generated files reported one group of 110 — 109 DELETE, `0.00` matched seconds on every row — where `-d 0 -p 0` over the same files reported none, because it took the index route instead. That put `index_is_cheaper`, a pure performance heuristic, in charge of a correctness question, and reached the exact state the `-d` cap at chance exists to prevent (one group, one survivor) through the flag nobody had bounded from below. The index route was quietly wrong at `-p 0` too, just less visibly — a proposed pair need not survive phase 2, so a scan of the local corpus at `-d 4 -p 0` reported 95 rows with `0.00` matched seconds; it now reports none, and the two routes agree at every `-p` as they are documented to. `-p 20` is byte-identical either side of the fix. The test is written as a separate `<= 0.0` rather than by turning the gate into `<=`, because `-p 100` must keep admitting a fully covered pair.

The consequence worth knowing before touching this: the file with the LOW coverage is normally the host, the host is the longer file, and length is the first ranking metric — so in a genuine clip/host pair the low-coverage file wins KEEP by construction and is never the one deleted. That protection is incidental rather than enforced. When the two coverages differ for some other reason (one file having several samples that all match a single sample of the other — a repeated or near-static frame — rather than one file containing the other) and the durations sit inside `DURATION_TOLERANCE_SECS`, length cannot separate them, the ranking falls through to size, and the low-coverage file can be the one marked DELETE. Still reachable at default settings, though the corroboration rule thinned it out a great deal: 3 of the 235 DELETE rows a default `-d 4 -p 20` scan of the local corpus produces (181 distinct files, some of them deleted in more than one group) share under 20% of their own runtime with a file their group keeps, against 11 of 167 before it. The pair to look at now is `archive/lat pulldown/lat pulldown_{21,22}.mp4` — 2.00 s and 2.40 s, `_21` marked DELETE having matched 0.07 s of its own 2.00 s. The example this paragraph used to name, `lat pulldown_{7,15}.mp4`, is no longer one: corroboration took that pair from 0.17 s / 1.14 s shared to 4.04 s / 5.00 s, which is what a genuine duplicate looks like. Report-only by default, and the report prints each row's own matched seconds next to it, so the information is in front of the user. Do not "fix" this by gating DELETE on the deleted file's own coverage without first working out what that does to clip detection.

**The length-protects-the-host argument has a second hole, and a single keyframe is enough to open it.** A file whose container holds one keyframe produces one hash, and `sample_times` gives the last sample an end of `total_ms` — so that lone hash stands for the entire runtime and the file's coverage is binary: 0% if nothing matched, 100% if anything did. No `-p` can gate it, because `max(cov_a, cov_b)` clears on its side alone. `archive/leg raises/leg raises_19.mp4` is 8.84 s with one keyframe; at `-d 10 -p 90` its hash landed within tolerance of 3 of the 10 keyframes in `leg raises_18.mp4`, giving 100% against 31.2%, and `_18` was marked DELETE despite 4.1 s of it having no match and being the higher-quality encode (237.8 vs 120.2 kb/f). Here the low-coverage file was the SHORTER one, so length ranked it *below* the file that was fully covered rather than protecting it.

**The corroboration rule closes that specific case and does not close the shape of it.** A witness has to be a different sample on *both* sides, so a one-hash file can never reach the loose tolerance and is held to `strict` — 8 bits at `-d 10`, where `_19`'s match sat at 10. That pair is gone from the `-d 10 -p 90` run and the genuine `_8`/`_10`/`_11`/`_15` cluster is untouched. What has not changed is the arithmetic underneath: a one-hash file that *does* match strictly still reads 0% or 100% and nothing gates it. The remaining levers are the same ones — a tighter `-d`, or a `--min-duration` floor. `--keyframe-interval` still cannot help: it only thins keyframes and never adds them.

**The extension list is a guess, and its two failure modes cost very different amounts.** `DEFAULT_EXTENSIONS` in `main.rs` is what a folder *walk* assumes a video is called — a named path is never filtered, per the `sources` module doc. An extension too many costs one file the decoder rejects, named in the run's problem list; an extension too few costs a folder that prints "No videos found" and a user who concludes the tool is broken. So the list runs to 18 containers rather than the original 6, and `.ts` is in it despite being how a TypeScript tree names every file: it is also how every DVB capture and half the camcorders on earth name their footage, and the failure it causes is loud and localised while the failure it prevents is silent.

**`-x '*'` is not a wider list, it is the absence of one, and no list could replace it.** A file with no extension has nothing for `Path::extension` to return, so no entry could ever name it — which made a DVD rip, a camera dump, or anything named by a content hash unreachable from a walk. `sources::Wanted` is therefore two shapes (`Anything`, `OneOf`) rather than a set, the wildcard wins over anything written beside it, and `-x '*.mkv'` is normalized to `mkv` because a shell user writes it that way and the alternative is a suffix that silently matches nothing. Under `Anything` the extension filter no longer turns directories away, so `walk_folder` checks `entry.file_type().is_dir()` first — WalkDir already knows, so it also saves a stat per folder in every other mode.

**A filename that is not valid UTF-8 is skipped where it is found, not mangled into a path that does not exist.** Every path downstream of `sources` is a `String` — cache key, report column, deletion target — so `ScannedFile::of` returns `Option<Self>` and the two callers record `unreadable` with "filename is not valid UTF-8". It used to go through `to_string_lossy`, which queued the file under a name with U+FFFD where the bad byte was and produced `Failed to process .../bad<U+FFFD> name.mp4: No such file or directory` — a missing-file error against a file the walk had just listed, blaming the decoder for a rename this tool had done itself. `read_path_list` has always handled a piped-in line this way; the walk simply did not. Never a safety problem (a lossy path cannot be opened, so it cannot be fingerprinted, so it cannot become a DELETE candidate) and it was already loud and exit 2 — what changed is which thing gets blamed. Decodability is settled **before** the inode is claimed, so an unusable name cannot stand in for a hard link that has a usable one, which would lose both.

**One report body is built per run, and which one is decided before the loop.** `wants_txt` / `wants_csv` / `wants_json` in `output_results` gate the three bodies; the text line is built when *either* the console listing or a `.txt` report will read it, and pushed only for the latter. Only the JSON tree was gated before, which was the cheap half: the text body is the whole listing accumulated in a `String` and the CSV is the whole listing again through a serializer, so a JSON run built both and a run with **no `--output` at all** still built both. Measured on the local corpus at `-d 18` (9,003 groups, a 31 MB CSV and a 17 MB txt), peak RSS: report-only run 66 → 18 MB, `-o x.csv` 67 → 50 MB, `-o x.json` 3.24 → 3.19 GB (the per-link tree dominates there, one object per pair). Wall time is unchanged to within noise, and all three formats are byte-identical either side. `test_each_format_still_carries_its_whole_body_now_that_only_one_is_built` is the guard, because the saving itself is invisible from outside and the failure it risks is an empty report.

**Where the report goes and how it is written are one decision, taken before any work starts.** `main::report_target_for` turns `--output` and `--format` into a `ReportTarget` (a `Sink` and a `Format`), which is also where the path check that used to be `check_output_path` lives; `export.rs` no longer parses a path to decide anything, and the extension is consulted in exactly one place (`format_from_extension`) and only when `--format` is silent. Three things fall out of that. `-o -` is stdout rather than a file named `-`, which it used to create — the parent of `-` is the working directory, so the check passed — and it works only because nothing else in a scan writes there: every result line, both progress bars and the confirmation prompt are on stderr. `./-` still names the file. A report on stdout also REPLACES the console listing rather than joining it (`console_for`): the two are the same run said twice, so `-o -` used to print everything to a terminal twice over, and a pipe still scrolled the whole listing past the user on the way to the line they grepped for. The summary is the exception, because a `.txt` report is exactly that listing plus that summary and the JSON carries the same figures under `summary`, while the CSV carries neither — so stderr keeps the receipt only for CSV. A report written to a FILE keeps both, because then the terminal is the only place the run is visible while it happens. Moving the listing to stdout by DEFAULT (so `vid-fp DIR | grep DELETE` needs no flag) was considered and refused: the listing and the summary are one document, so the summary would have to follow it and `vid-fp DIR --delete > /dev/null` would discard the receipt for a destructive run, or stay behind and leave `vid-fp DIR > report.txt` no longer holding the txt report. It would also make the aligned human table, the one output format with no stability promise, the surface pipelines get built on. `-o -` is the opt-in and stdout stays empty otherwise. `--format` with no `-o` is refused rather than read as "and put it on stdout", because turning a run that writes no report into one that does is not a default worth guessing at. And a broken pipe on stdout (`-o - | head`) is swallowed in `write_report` rather than recorded as `report_write_failed`: a reader closing early is how a pipeline ends, not a run that did less than it was asked. Every other write failure is still a problem and still exit 2.

**Nothing is destructive without `Disposal`.** `export.rs` cannot touch a file unless `main::disposal_for` constructed one from `--delete` / `--permanent` / `--move-to`. `--from-report` is no exception: it bails with an explanation rather than reading a report it could not act on.

**The `--move-to` loop guard asks about the REQUEST, not about what the request found.** `sources::collect` returns a `Library` — the files, plus the folders that were walked and the `--exclude` paths that resolved — and `Library::walk_reaches` answers "would a scan of this same request find a file moved to `dest`". It used to be asked of the parents of the found files, which is the same question only in a flat library: `vid-fp lib -r --move-to lib/dupes` over a tree whose videos all live in `lib/sub` proposed no parent that enclosed `lib/dupes`, so it sailed through, and the NEXT run re-ingested what it had moved, kept that copy and moved the original in beside it — two runs to empty a library into `dupes/`. Putting the destination one level deeper (`lib/sub/dupes`) was caught, which is what made it easy to miss. A folder is a scan root by having been pointed at, not by having yielded anything: one that is empty today is one a moved file is found in tomorrow. Excludes are honoured because the refusal's own advice is to exclude the destination, and under the parent-based check that advice did not work — the root still enclosed `dest` whatever `-e` said. Nothing else earns an exemption, including a non-recursive walk: the landing paths sit at least two levels under `dest` so today's run would not reach them, but the destination is still inside the library and one `-r` later it is the same loop.

**`export::dispose_one` is the only copy of the destructive step**, and it takes a path and the size that file was measured at — nothing else. That narrowness is what made `--from-report` cheap, and it is worth preserving: widening it to need a `VideoFingerprint` again would mean the report mode either re-fingerprints or grows a second, weaker version of the staleness check. Both callers pass a size from the same moment the delete decision was made (the scan; the report's `size_bytes` column), and a file that no longer matches it is reported CHANGED and left alone. `fingerprint_video` therefore takes `file_size` as an argument rather than re-stat'ing: the fingerprint's size and its stamp's size are then one measurement from one moment, and a file that grew between the scan and its own decode reads as CHANGED instead of being deleted against a figure nothing else in the run agreed with.

**`report.rs` trims every cell it reads except the path.** Leading and trailing spaces are legal in a filename and both writers emit them verbatim, so trimming `full_path` meant the tool could not replay its own report — it looked up a *different* path, and the size check is taken against whatever survived the trim, so a same-sized neighbour was deleted instead. A whitespace-only cell is still treated as empty.

**A report's DELETE rows are the user's decision, not the tool's.** The safety rules below (direct measurement, one survivor per codec, a ranking that only condemns a file against a copy it was measured against) are enforced by the run that *writes* a report. `report.rs` deliberately re-imposes none of them — a group may be emptied completely, which the writing run can now do on its own too — because the file has been edited by then and second-guessing it would defeat the point, which is adjudicating REVIEW rows. What it does keep is the confirmation prompt, the size check, and a hard rule that an action word it doesn't recognise is never guessed at: the file is left alone and `stats.report_unusable` fails the run. Columns are located by header name (and JSON fields by key), which is what lets the CSV layout be chosen for whoever reads it: reports written by older builds, and reports a spreadsheet handed back reordered, replay identically. What a row is *called* in a complaint is per-format on purpose — `line 14` for the CSV, `group_1 file 2` for the JSON, which is how each is actually navigated — because a complaint about a row the user cannot find is one they cannot act on.

**The confirmation sits between the two passes of `output_results`, not at start-up.** `confirm::approve` is asked once the DELETE set is resolved, because that is the first moment there is a count and a byte total to show. Declining does not abort: it rebinds `disposal` to `None` for the rest of the function, so the labels, the summary and the JSON all describe the run the filesystem actually saw. It is interactive-only (`stdin` *and* `stderr` must be terminals) so a pipeline can never block on it, `--yes` skips it, and everything that isn't an explicit yes — EOF, a read error, an interrupt, three unparseable answers — leaves the files alone.

## Keeping the docs honest

`README.md`'s options table, the `Args` doc comments (which become the man page and `--help`), and the tuning/safety prose describe the same behaviour three times. Any flag or default that changes has to be updated in all three. Report formats are `txt`/`csv`/`json`, resolved once in `main::report_target_for` and written from the `Format` it produces.

**No column position is load-bearing, and it is worth keeping it that way.** The CSV order used to be frozen by two readers that indexed into it, so every new field was bolted onto the right-hand end regardless of what it meant, and `action` ended up five columns from the link data that justifies it. Both readers now resolve columns by header name — `report::column` and `local_accuracy_test::get_duplicate_files` — which is also what lets the golden `vd_results_*.csv` baselines beside the corpus stay useful: they were written by older builds with a different, shorter layout. Reorder the report freely; just never re-introduce an index.

**Every column in the link block answers for the row's own file.** That is what the `matched_` prefix promises, and it replaced a `shared_` block that broke the promise: `matched_seconds` used to be `overlap_seconds`, the pair's reconciled minimum, sitting beside a range that was this file's — so a row whose matched footage ran `0.00`–`8.84` reported `1.88` of it and read as a malfunction, with nothing in the row to say one of the numbers had changed subject. `MatchIndex::matched_seconds` is now `coverage × duration` for that row alone. On an honest match this changes no number, because both ends already agreed (a clip's `100% × 2min` and its host's `9% × 22min` are both two minutes); it only diverges on lopsided pairs, which is the case worth seeing. `overlap_seconds` survives with exactly one caller, `--min-duration`, and the two are no longer at risk of the drift that once had the gate taking the higher estimate and the report the lower — they answer different questions now. Coverage is taken over `duration` rather than `total_ms` so the figure stays under both the `length` column and its own envelope; `sample_times` only ever extends the runtime, so `total_ms >= duration * 1000` always.

`samples` (the fingerprint's hash count) is in the report because it is what makes that block interpretable — an envelope much wider than the footage is either a scattered match or a file too coarsely sampled to know, and only the sample count separates them. It is a property of the file, not of the link, and it still sits between `matched_with` and `matched_seconds`: it qualifies the figure it precedes, and that beat the block it belongs to. `framerate` is the sole figure carried raw-only, by request; its formatted form lives on the console line.

The three formats are one layout expressed three ways, and `export.rs` writes them from a single pass, so a field added to one is added to all three in the same place. The JSON's key order is only preserved because `serde_json` carries the `preserve_order` feature — without it serde_json's `Map` is a `BTreeMap` and the tree comes out alphabetized, which interleaves each figure's raw and formatted halves and buries `summary` under the whole results array.

The JSON tree is built only when `--output` ends in `.json` (`wants_json` in `output_results`). It carries one object per measured link per file, so building it unconditionally made a report-only run pay for a structure it then discarded.

Releases are cut by pushing a `v*` tag — `.github/workflows/release.yml` runs `scripts/build-ffmpeg-static.sh`, builds the static binary against it, generates completions and the man page from the binary itself, and uploads a versioned copy, a stable-named copy, the extras tarball and the LGPL relink kit. The tag build now runs `cargo test --release --locked --features static-ffmpeg` between the build and the DT_NEEDED check, so the suite runs against the exact artifact that ships and against the vendored FFmpeg 8 — the feature flags have to keep matching the build step above it, or the test run replaces the static binary with a dynamic one and every check after it inspects the wrong file.

`.github/workflows/ci.yml` runs `cargo clippy --all-targets --locked -- -D warnings`, `cargo test --locked` and a `cargo check` on the declared MSRV, on every push to a branch. **It is a clean-checkout gate, not a correctness gate.** `tests/local_accuracy_test.rs` and `benchmark/` are gitignored, so a clean checkout is 25 files and CI never sees the accuracy harness at all — it proves the committed tree compiles standalone with a cold target dir and a fresh registry, which the development machine cannot prove, and it proves nothing whatever about grouping. Accuracy is still measured by hand. There is no `cargo fmt --check`, because the tree is not rustfmt-clean.

**`cargo clippy --all-targets` is clean, and three `#[allow]`s are what keep it that way.** Each carries its reasoning at the site; the short version is that all three lints are asking for a rewrite that would cost something real. `clippy::unnecessary_cast` on `AV_CODEC_FLAG2_FAST as i32` (`fingerprint.rs`) — the FFmpeg flag macros have no declared type, so bindgen infers one per `#define`, and within a single header the `AV_CODEC_FLAG_*` family lands on `c_uint` while most of `AV_CODEC_FLAG2_*` lands on `c_int`; the cast is redundant only for as long as this flag keeps its current bit. `clippy::needless_range_loop` on the variance/auto-crop scan (`fingerprint.rs`) — `y` and `x` index two flat 64×64 buffers *and* two 64-entry projections, one of which is re-walked per row. `clippy::too_many_arguments` on `output_results` — the two parameters that shared an axis are already `Policy`, and a bag for the rest would only hide which of them the destructive pass reads. Do not "fix" these by deleting the comment and taking clippy's suggestion.

Two release steps are load-bearing rather than decorative, and both guard failures that are silent in ordinary testing: one greps `DT_NEEDED` for `libav*`/`libsw*` and fails if the binary linked FFmpeg dynamically after all, the other fingerprints a generated AV1 clip. FFmpeg's built-in AV1 decoder is hwaccel-only, so a configure that quietly drops `libdav1d` yields a binary that passes every other test and cannot fingerprint a single AV1 file.

**The LGPL relink kit is a licence obligation, not an extra.** FFmpeg is LGPL 2.1+ and the link is static, so §6 requires shipping the means to relink — hence the `.a` archives, headers, build script and `RELINKING.md`. Keep `--disable-gpl --disable-nonfree` in the configure line: `vid-fp` is offered under Apache-2.0, which is incompatible with GPL-2. See `THIRD-PARTY-LICENSES.md`.
