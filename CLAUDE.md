# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

## What this is

`vid-fp` — a Linux CLI that finds duplicate videos and clips by perceptually fingerprinting their keyframes. Binary-only crate (`[[bin]]`, no `lib.rs`); the README is the user-facing spec and the man page is generated from the clap `Args` doc comments.

## Build and test

A plain build links the system's **shared** FFmpeg. On Debian/Ubuntu: `libavcodec-dev libavformat-dev libavutil-dev libswscale-dev clang pkg-config` — only those four libav\* libraries, since `ffmpeg-next` is pinned with `default-features = false` (avdevice and avfilter are unused and were dragging libavc1394 and libncursesw into `DT_NEEDED`).

`ffmpeg-next` is pinned to **8.1**, and that is deliberately newer than any FFmpeg you are likely to have. Only the crate's *forward* compatibility is broken: 8.1 compiles and runs correctly against FFmpeg 6, 7 and 8 headers because `ffmpeg-sys-next` detects the version and gates the wrapper on cfgs, whereas the 6.x crate fails against FFmpeg 7 headers with ~30 errors inside the dependency. Pinning the newest widens the host range; do not lower it to match what the release vendors.

The **released** binary is different: it statically links a vendored FFmpeg 8 + dav1d, so it needs no FFmpeg at all at runtime.

```bash
./scripts/build-ffmpeg-static.sh   # ~10 min, once; -> ./ffmpeg-static (gitignored)

cargo build --release --features static-ffmpeg              # what ships
cargo test  --release --features static-ffmpeg -- --nocapture
```

`build.rs` defaults to `./ffmpeg-static`, so no env var is needed day to day; `FFMPEG_DIR` overrides it for CI and for anyone relinking. **Do not export `FFMPEG_DIR` from a shell profile** — `ffmpeg-sys-next` reads it whether or not the feature is on, so a plain `cargo build` would then try to link the static archives and fail at `ld`.

**Pass `--features static-ffmpeg` to `cargo test` as well as `cargo build`.** `cargo test` builds the bin target too, so a bare `cargo test --release` silently overwrites `target/release/vid-fp` with a *dynamic* binary and then measures it against the static baselines — which shows up as a `4-20` failure reading 75/186 that looks exactly like a real regression. The harness prints a warning when it detects this, but the warning is easy to scroll past.

**Accuracy numbers only mean something from the static build**, because the golden CSVs were taken with it — see the accuracy-test note below.

```bash
cargo build --release --locked     # release profile: lto + codegen-units=1; use it for any timing
cargo clippy --all-targets
cargo test                          # unit tests (in-file `mod tests`) + the accuracy integration test
cargo test --bin vid-fp share_for   # single unit test — tests live in the binary, so --bin, not --lib
cargo test --test local_accuracy_test -- --nocapture
```

`tests/local_accuracy_test.rs` is a machine-local regression harness: it shells out to `./target/release/vid-fp` against `/home/daniel/Documents/AN` with a ladder of `-d`/`-p` settings and asserts exact group/file counts against baseline CSVs stored in that folder. It **returns early and passes** when the directory is absent, so a green `cargo test` on another machine proves nothing about accuracy. Build release first — it runs the binary, not the crate.

**Build it with `--features static-ffmpeg` before trusting the result.** The baselines were re-taken against the vendored FFmpeg 8, and the `4-20` profile is genuinely FFmpeg-version-sensitive: a dynamic build against FFmpeg 6 reports 75/186 there where the static one reports 74/184, because one pair's coverage falls by a single 0.5 s hash sample and drops under the 20% gate. The other two profiles agree across both. That profile has always sat within a percent or two of its gate — it is the same one that moved for the PTS→DTS fix — so treat a lone `4-20` diff as a question about which FFmpeg produced it before treating it as a regression.

`src/fingerprint.rs` tests decode `tests/fixtures/test_video.mp4`, so unit tests need a working FFmpeg at runtime too.

## Pipeline

`main::run` drives one linear pass; every stage polls `utils::shutdown_requested()` and returns `Outcome::Interrupted` rather than unwinding.

1. **`sources::collect`** — walks folders / reads stdin or `--from-file`, stats each file exactly **once**, and deduplicates on `(device, inode)` so symlinks, hard links and overlapping scan roots collapse to one entry. Everything downstream (cache stamp, sort, thread weights, prune) reads the `ScannedFile` fields; nothing re-stats. What comes back is a `Library`: those files, plus the walked folders and resolved excludes the `--move-to` loop guard needs — see that invariant below.
2. **Cache pass** — files are sorted largest-first, then *every* cache lookup happens before *any* decode. This split is deliberate: interleaving them under rayon let one slow decode block cached neighbours in the same work slice.
3. **Weighing pass (`fingerprint::weigh_decode`)** — every cache *miss* is opened once, header only, and asked how much decoding it implies; `todo` is then re-sorted on that. Like the cache pass it is complete before any decode starts, because the thread budget and the progress bar are both apportioned against the total. A file that will not decode at all, and a file that is not GOING to be decoded because it is shorter than `--min-duration`, are both settled here and dropped from `todo` rather than scheduled — see the `Weighed` invariant below. It has a bar of its own (`weighing_bar`), which counts files because nothing has measured any work yet.
4. **`fingerprint::fingerprint_video`** — decodes keyframes only, box-filters each to 16×16, DCT-transforms, and keeps the 8×8 low-frequency corner as a 64-bit hash (exactly 32 bits set, hence only even `-d` values are meaningful). Featureless frames (black, fades, title cards) are dropped below `MIN_AC_ENERGY` so they can't link unrelated files, and a file with nothing else in it fails rather than fingerprinting to nothing — see the all-featureless invariant below. Sample times are **milliseconds of decode time accumulated from the first keyframe**, not PTS — MP4 `ctts` skews PTS once non-key packets are discarded, and a container that restarts its clock mid-file makes an anchor meaningless (see the splice invariant below). The demux loop ends when the input is spent, whatever the demuxer calls that — see the infinite-loop invariant below.
5. **`compare::find_all_matches`** — two phases. Phase 1 builds a `BlockIndex` over each of 4 16-bit hash blocks and proposes candidate pairs; the probe radius is `Tolerance::widest() / 4` with nothing capping it, so it is exhaustive at every tolerance, and `index_is_cheaper` skips the index entirely (comparing every pair outright) once the probe grows wider than the library. Phase 2 compares every proposed pair exactly, against **two** tolerances rather than one — see the corroboration invariant below. Coverage is **directional and measured in milliseconds of runtime**, not in frame counts — a hash stands for the span until the next sample, so two encodes sampling at different rates still agree on how much footage overlaps. Phase 2 runs under a progress bar (`verification_bar`), because at a loose `-d` it is minutes of silence after phase 1's one-line "verifying..."; workers batch their reports through `Ticker` for the same reason the decode stage has `PROGRESS_STEP_BYTES`.
6. **`clustering::find_duplicate_groups`** — maximal cliques via Bron-Kerbosch with Tomita pivoting, run **per connected component** and under a ceiling. A group asserts "every one of these matched every other", which is what lets `export.rs` rank them against each other. Adds no thresholds of its own — the ceiling is not one; it is a refusal to answer, and it is counted as a problem. Groups therefore **overlap**: a file can be reported in several, and the report is a list of relationships rather than a partition of the library.
7. **`export::output_results`** — ranks inside each group but resolves each file's label ONCE across all of them (REVIEW > DELETE > KEEP), performs the disposal, and returns the paths that moved so `main` can drop their cache entries.

`utils` holds the ranking rules (`GroupMaxima`, `find_best`), formatting, and the shutdown flag. `stats::RunStats` tallies **skips** (intentional: `--min-duration`, excludes, inode aliases) separately from **problems** (the run did less than asked) — only problems set exit code 2.

**`--from-report` is a second entry point that skips all of it.** `run` branches to `main::run_from_report` before anything touches the filesystem; `report::apply` reads a report an earlier run wrote, takes the rows whose `action` says `DELETE`, and disposes of exactly those. It shares four things with the grouped path and nothing else: `confirm::approve`, `export::dispose_one`, `export::disposed_line`/`trouble_lines`, and `cache_forget`. It works because the destructive step only ever consults a path and a size, and both are report fields — see the `dispose_one` invariant below.

**Both formats that record a size are readable, and only the extraction is per-format.** `report::read` dispatches on the file's first non-whitespace byte (`looks_like_json`): `{` or `[` goes to `read_json`, everything else to `read_csv`. It used to dispatch on the extension, which worked only for as long as the writer did too — `--format` made `-o dupes.bak --format json` writable, and that report would have gone to the CSV reader and been refused for want of columns it was never going to have. The sniff is also what gives a JSON array named `.csv` the complaint about its missing `results` key rather than one about a missing column. What is NOT duplicated is the judgement — a format reader pulls three cells out of one row and says where that row was, and every question about what those cells mean is answered once in `Rows::consider`, for rows of every format. That is the whole answer to the objection the module doc used to carry, that a second parser would be a second place to be wrong: it is, only if it is allowed to decide something. `test_every_report_format_that_records_a_size_can_be_handed_straight_back` (in `export.rs`, where the writer lives) runs a real report through each format and back. The JSON's rows are the `results[].files[]` objects; the `matches` array nested under each carries a `full_path` too and is deliberately never read, because it names the file that row was measured *against* — the one that WON. `.txt` stays unreadable, and that is a property of the format: it records no size, so there is nothing to check a file against before removing it.

## Invariants worth knowing before you change things

**`-d` is two thresholds, and the second one needs a witness.** `Tolerance::for_distance` turns the flag into `strict = -d` and `loose = -d + 1.5 sigma` (6 bits on a 64-bit hash). A frame match inside `strict` is taken outright — so `-d` keeps the meaning it had before corroboration existed — and one between `strict` and `loose` is taken only if a *different* frame of each video also matches within `ALIGNMENT_TOLERANCE_MS=500` of the same time offset (`compare::corroborated`). Both halves move with every rung and **neither is clamped against a constant**, which is what keeps the flag a sensitivity control; `test_the_tolerance_pair_moves_monotonically_with_the_flag` pins the monotonicity the docs promise.

**Every threshold here is stated in sigma, not in bits, and that is load-bearing.** The distance between two unrelated hashes is Binomial(`HASH_BITS`, ½): mean 32, sd `sqrt(HASH_BITS)/2` = 4 for this hash. `sigma()` and `sigma_below_chance()` are what turn "1.5 sigma" into 6 bits and "5 sigma below chance" into 12. A bit count means nothing without the width it came from — widen the hash and a hard-coded 12 silently becomes a *tighter* rule, where 5 sigma stays 5 sigma. This replaced an earlier pair of fitted constants (`UNCORROBORATED_BITS = 8`, `CORROBORATED_BITS = 12`) that clamped both sides; see the design note below for why they had to go.

The measurement that justifies corroboration at all, taken over `benchmark/labels.csv`: among pairs the human labeled SAME, sample pairs landing within 0.25 s of each other are within 4 bits 64% of the time and within 12 bits 75%; among pairs labeled DIFFERENT the same temporally-coincident sample pairs are within 4 bits **0.0%** of the time and within 12 bits 0.6%. Distance alone cannot separate those two populations — 152 of the 181 SAME pairs the old code missed at `-d 4` had no frame pair within 4 bits at all, while their best frames sat at 6-12. Distance *plus* agreement about when is what separates them.

**How many witnesses is set by how often chance produces a match that close, not by a constant.** `witness_schedule` reads `chance_orders_of_magnitude(x)` — `-log10 P(two unrelated hashes land within x bits)`, the Binomial tail — and asks the cluster (the match plus its witnesses) to carry `CORROBORATION_BUDGET = 2` times what one match at `EVIDENCE_ANCHOR_SIGMA = 5` sigma below chance carries. That is 1 witness out to 12 bits, 2 at 14, 3 at 16, 4 at 20. The budget and the anchor are **one calibration between them**, not two: 2 is the value that puts the anchor at exactly one witness, and `test_one_witness_is_exactly_enough_at_the_anchor` fails if they drift apart. The independence the arithmetic assumes is not real — near-static footage produces matches that corroborate each other for nothing, which is why a witness must be a different sample on *both* sides, and must differ on both sides from every OTHER witness as well — so only the SHAPE comes from the tail.

**The quota counts distinct samples, not matching pairs, and that distinction is the whole of it.** Witnesses used to be tested against the candidate alone (`wi != i && wj != j`), so the count was over matching PAIRS: a 2x2 block of mutually matching frames is two samples a side and four witnesses, which paid a quota of four with two coincidences. That is exactly the near-static case the sentence above says the rule exists to refuse, and it made the schedule's arithmetic — `m` matches are roughly `m` independent coincidences — untrue of the thing being counted. Witnesses must be distinct from each other on both sides as well as from the candidate, which makes them a matching rather than a count. It is **unreachable below `-d 7`**: the quota is 1 out to 12 bits and `loose = -d + 6`, so every rung up to `-d 6` asks for one witness and distinctness among one witness is vacuous — `-d 4 -p 20` is byte-identical, and so is the `6-15` accuracy profile. Where it does reach, measured against `benchmark/labels.csv` after the 77 pairs it moved were labeled (2026-08-21): `-d 8` 96.8% -> 97.0% precision, `-d 10` 95.0% -> 95.4%, `-d 12` **72.4% -> 76.4%** with F1 0.822 -> 0.847. **Every one of the 32 pairs it drops that had never been judged is DIFFERENT**, and all six SAME pairs among them are kept. It costs one SAME pair at `-d 10` and one at `-d 12`. The DELETE audit falls 9 -> 8 wrong at `-d 8`, 10 -> 9 at `-d 10` and 60 -> 51 at `-d 12`, with no wrong deletion added at any rung. Cost is nil warm out to `-d 18` and 2.8 s -> 5.3 s on the whole local corpus at `-d 24`, where the quota reaches 8 and the window scan stops early-exiting.


**Which witnesses those are is a maximum matching, and greedy was not, which cost the flag its monotonicity.** A witness must differ from the candidate and from every other witness on BOTH sides, so the witnesses of one alignment window are a matching in a bipartite graph — samples of A on one side, samples of B on the other, one edge per frame match — and the quota is met when the largest matching reaches it. Taking them greedily in offset order answers a different question: it is a lower bound on that matching, and a *wider* `-d` can make the bound worse. A match the looser tolerance newly admits can sort earlier, be taken first, and consume both sides of two matches that would have paid the quota between them. Constructed at 14 bits with a quota of two and one 16-bit blocker a bucket earlier, `-d 8` marks the candidate and `-d 10` does not — the flag the README promises only ever adds files, removing one, and by a route that has nothing to do with the clustering ceiling that was until now its only documented exception. `compare::Witnesses::enough` decides the matching exactly instead, and adding an edge to a bipartite graph can only raise the largest matching, so the property now holds by construction.

**Four questions come before the search, and every one of them is exact.** Deciding the matching outright for every candidate is what a correct rule costs if it is written naively, and that is 13% of phase 2 at `-d 24` (5.40-5.56 s against 4.73-4.86 s for greedy, over 58.7 million candidates). In ascending order of cost: is the window even long enough to hold `needed` rows; did the greedy pairing reach the quota (a pairing IS a matching, so that settles it, and it is the whole rule out to 12 bits where the quota is one); did greedy fall below HALF the quota (what greedy leaves is a *maximal* matching, so the largest is at most twice it); and does the window hold `needed` distinct samples on each side (a matching pairs one sample with one sample, so it cannot outrun the smaller side). Measured at `-d 24`: 5.65 million candidates reached the fourth question, 5.54 million died on it, and 107 thousand built a graph. **The first question is the one that pays for all of it** — it costs nothing, because `corroborated` now tracks both edges of the alignment window as it walks instead of walking out from each candidate (both edges only move forward, so one pass finds them all), and the greedy rule never asked it. The search that remains is bounded by König: a window keeping `needed * (needed - 1) + 1` edges is over the quota whatever they look like, since no vertex is allowed more than `needed` edges, and both the collecting walk and the matching stop there. Take any one of the four out and the rule costs more than the greedy one it replaced. Two of those four rest on properties of the caller rather than of the window, and both are stated on `Witnesses::enough`. The window-size bound is `window.len() <= needed`, not `<`, because the candidate's own row is always one of the rows (`corroborated` passes `aligned[lo..hi]` with `lo <= k < hi`) and `eligible` drops it -- a window can only ever offer `len() - 1` witnesses, and a `debug_assert` in that arm is what makes a synthetic window built without the candidate's row fail loudly instead of quietly answering the wrong question. The degree cap keeps a matching of size `needed` if one existed only because each edge is a DISTINCT pair of samples, which `for_each_frame_match` guarantees by visiting each pair exactly once; two copies of one edge would spend a vertex's budget on a single neighbour and could then turn away the edge that paid the quota. The cap is also asked of the SLOTS rather than of freshly made vertices, so an edge it drops leaves nothing behind: creating them first put isolated vertices in `side_a`, which `untried` is derived from, weakening the "what is left to gain" exit -- and put the search in a state the `debug_assert` that used to stand after the collecting loop said was impossible, so a `cargo test` build panicked on any pair where a file has more samples than the bitmask holds and the window is one-sided. That assert is now an exact exit (`side_a.len() < needed`), which is the same question `side_is_wide_enough` asks, over what the collecting loop really kept rather than over what the window offered — the two differ because the degree cap can drop every edge a sample had.

**The fourth question is asked of a file of any length, and it was not.** `side_is_wide_enough` marks a bit per sample, so it is exact only while the samples fit in the word, and past `u64::BITS` it used to give up and return `true` — excused in its own doc on the grounds that a file with more is a long video whose pairs are the expensive ones anyway, which is the argument FOR the cheap rejection rather than against it. 3.3% of the local corpus is over 64 samples, and every candidate of theirs that reached here built a graph. It also meant the property the name states was never established for those pairs at all, which is what the `debug_assert` above was asserting: at `-d 10` (quota 3, since `loose` is 16 there) a 2x2 block of mutually matching frames on a pair with a long file fires it, so **every debug build aborted** — `./target/debug/vid-fp ~/Documents/AN -r -d 10 -p 20` was 18 panics and exit 101, while the release build reached the right answer by the `untried` exit and `cargo test` stayed green because no unit test built a pair that wide. A wider file now takes `wide_sides_are_wide_enough`, which decides the same question by collecting distinct samples into two arrays capped at `needed` and stopping the moment both sides reach it, so nothing in it grows with the sample count. Two routes to one predicate is what this file otherwise avoids, and it is bought because the narrow one is the hot one: putting every pair through the collecting route costs ~1.5% of wall time at `-d 24`, for a verdict identical by construction. `test_the_cheap_exits_agree_with_the_matching_they_stand_in_for` now walks all 4,000 of its windows past BOTH routes, declaring the same window narrow and then wide, so the collecting route cannot refuse a window the bitmask would have allowed. It cannot catch the opposite, and nothing testing verdicts can: a route that gives up and says `true` still reaches the right answer through the graph, which is precisely how the old one survived every test there was. So the refusal itself is asserted directly, on the predicate rather than through `enough`, in `test_a_file_too_wide_for_the_bitmask_still_needs_witnesses_on_both_sides`. Reports are byte-identical at `-d 0, 4, 8, 10, 12, 14, 16, 18` and `24`, the accuracy harness passes on all three profiles, and interleaved `-d 24` timings are 4.99 s against 5.02 s over ten runs each — the same, within an ordering effect large enough that whichever binary runs first wins.

`test_a_wider_tolerance_never_takes_a_frame_match_away` pins the constructed case, `test_no_rung_of_the_tolerance_reports_less_than_the_one_below_it` walks a `-d` ladder over 200 pseudo-random pairs, `test_witnesses_are_paired_off_rather_than_counted_up` pins all three arms of the decision — greedy, the edge bound, and the augmenting search that is only reachable from a quota of three up — and `test_the_cheap_exits_agree_with_the_matching_they_stand_in_for` walks 4,000 pseudo-random windows past all four exits and compares every verdict against a brute-force maximum matching that shares no code with them, which is the only guard that says the exits are the same question rather than a cheaper one.

Measured on the local corpus: reports **byte-identical at `-d 4`, `6`, `8` and `10`** (the quota is one witness out to 12 bits and a matching of one is a witness of one), and 1, 7 and 18 links added at `-d 12`, `14` and `16` against 631, 981 and 3,282, with **none taken away at any rung**. Those are rungs where precision is 84% and falling; the single added pair the labels reach is DIFFERENT, and P/R among judged pairs is unmoved at `-d 14` and `-d 16` (`-d 12` precision 83.8% -> 83.6%, F1 0.886 either way). So it is not bought for accuracy — it is bought so the monotonicity claim is true. The three accuracy-harness profiles pass unchanged. It is also not bought with time: warm wall time on the whole corpus, three runs each, is 0.10-0.11 s against greedy's 0.11-0.12 s at `-d 4`, 0.19 s either way at `-d 12`, 0.88-0.92 s against 0.89-0.92 s at `-d 18`, and 5.11-5.28 s against **5.41-5.49 s** at `-d 24`, where the window-size question more than pays for the exactness. Peak RSS is unmoved. The AN corpus never showed the lost match on its own — the reported file set is strictly monotone at every rung under both rules — so this is a property fixed at its source rather than a bug anyone hit.

The scratch space (`Witnesses`) is **one per phase-2 worker, not one per pair**: `find_all_matches` builds it in the `map_init` of both rayon arms and hands it down through `measure_pair`. Its buffers are cleared per candidate and grown at most once per worker, so the ordinary path allocates nothing at all; per-pair construction cost 0.2 s of the 5.3 s at `-d 24` on its own. The slot arrays it indexes by sample number are grown lazily inside the search, because a pair whose every candidate is settled by one of the four questions above never indexes them. `Rule` (the tolerance pair plus the witness schedule) exists so those call chains stay under clippy's argument limit without a fourth `#[allow]` — they are one calibration and are read together everywhere.

**Measured, links scored against the hand-labeled pairs.** Every rung beats the flat single threshold it replaced (`F1`, SAME): `-d 0` 0.406 -> 0.715, `-d 2` 0.684 -> 0.791, `-d 4` 0.762 -> **0.859**, `-d 6` 0.827 -> 0.909, `-d 8` 0.887 -> 0.931, `-d 10` 0.918 -> 0.939, `-d 12` 0.914 -> 0.915. Precision at the default is 99.7% (one false positive), and the ladder walks it down smoothly: 99.2, 98.3, 96.0, 88.5. The honest way to read the gain is at MATCHED precision, which does not depend on where this corpus's knee sits: at ~99.5% precision the flat rule reached 79.8% recall and this reaches 86.0%; at ~97%, 86.4% against 91.1%; at ~91%, 92.1% against 93.4%. The curve moved, not the operating point.

The cost is 0.13 s of warm comparison time on the 756-file corpus (0.07 -> 0.20 s, against 175 s of decode) and nothing measurable in peak RSS (522-524 MB either way, inside the run-to-run spread); the fingerprints are untouched, so **this needed no `CACHE_TABLE` rename and no re-decode**. Cold wall time is 175.3 s for the old binary and 174.9/175.3 s for the new one across an interleaved batch — the same, and the reason the batch has four runs is the documented first-run effect (153.8 s, whichever binary goes first).

**Why the clamped version was abandoned, so it does not come back.** The first version of this rule was `strict = min(d, 8)`, `loose = max(d, min(d + 8, 12))`. It scored better on this corpus at the loose end — 99.3% precision at `-d 12` against 88.5% — and it was still wrong, for a reason no accuracy number shows: `loose` reached its ceiling at `-d 4`, so `-d 4, 6, 8, 10, 12` differed only in the lone-match side and produced 470, 479, 490, 490, 490 pairs. Five rungs of a sensitivity knob doing nothing, with the flat stretch positioned by whichever corpus the two constants were fitted to. **A knob whose range is fitted to one library does not generalise, however well it scores on that library.** If you are tempted to add a ceiling back, the thing to check is not F1 — it is whether every rung still moves.

Measured alternatives, so they need not be re-derived (all at `-p 20`, scored on the same labels): `strict = -d - 2, loose = -d + 2` scores *worse than a flat threshold* below `-d 10` (0.744 against 0.762 at `-d 4`) because the lone matches it gives up cost more than a narrow corroborated window wins back; `loose = -d + 8` buys recall at the default (0.903) and gives it back from `-d 10` up, where the strict side is what starts admitting false positives; removing the schedule and letting any cluster size pay for any distance collapses to 83.9% precision at `-d 2`, because that is where the independence assumption fails hardest.

Three consequences worth knowing before you touch it:

- **Phase 1 must probe at `loose`, not at `-d`.** A pair whose only matches are corroborated ones is never proposed otherwise, and the rule would be unreachable exactly where it earns the most. At the default this makes the probe radius 2 instead of 1.
- **Every frame match is judged on its own distance**, so one pair can be admitted on a mixture — a 4-bit match taken outright, a 10-bit one with a witness, a 16-bit one with three. There is no per-pair notion of "how good the match was" anywhere in `match_overlap`, and the coverage figures the report prints cannot tell you which kind carried a pair.
- **A file with one sample can never be corroborated**, because a witness must be a different sample on *both* sides. This closed the bad DELETE in [[single-keyframe-files-defeat-match-percent]]: at `-d 10 -p 90` the `leg raises_18`/`_19` pair, which used to be admitted on `_19`'s lone hash reading 100% covered, is gone, and the genuine `_8`/`_10`/`_11`/`_15` cluster still stands.

**One run per cache, and `--cache` is the only way around it.** redb takes an exclusive `flock` when the database is opened, and the handle lives for the whole of `main`, so the lock covers the entire scan rather than the cache pass — a second concurrent run cannot be made to share it by any amount of retrying, which is why there is no wait-and-retry flag. `resolve_cache_path` picks the file (XDG default, or `--cache`, which accepts a directory and puts `CACHE_FILE_NAME` inside it) and `open_cache` is the only place that opens it. That function matches `DatabaseError` rather than wrapping it, because contention, a format upgrade and a permissions problem want three different sentences and the single `.context()` this replaced gave all four failures one sentence with no path in it. The legacy sled sweep stays on the default location only; superseded-table retirement applies to any cache, since a user's own cache file goes stale the same way.

**`--from-report` is the one mode that runs without a cache, and only a locked one.** It reads nothing out of the cache — the single call is `cache_forget` after disposal — so refusing to replay a report the user has already reviewed would block a deletion for as long as some unrelated scan takes. Worse, the advice the locked message gives would be wrong there: a cache handed over with `--cache` is not the one holding those entries, so the run would delete the files and purge nothing, silently. `main` therefore degrades to `db: None` on `CacheUnavailable::locked` alone, and only for that mode; `run` and `run_from_report` take `Option<&Database>`. The purge is given up loudly — a warning before the confirmation prompt, `cache_purge_failed` in the problem summary, exit 2, `--prune-cache` collects the entries later. `--clear-cache` is exempt, because emptying a cache is the thing that was asked for rather than bookkeeping. Every other open failure is still fatal in every mode, which is what `locked` exists to distinguish.

**`--prune-cache` refuses to run against a scan that fell short, and `prune_obstacle` is the whole of that rule.** A prune keeps exactly the entries whose file is in front of the run and removes every other one, so it is only ever as correct as the scan is complete. It used to run before the `video_files.is_empty()` check and against whatever the scan produced, including nothing: `vid-fp vidz --prune-cache` with `vids` meant printed "Could not resolve", pruned every entry it had, and then said "No videos found" — hours of decode discarded by one keystroke, by a run that had already recorded the failure and knew it would exit 2 for it. The obstacles are `unresolved_includes`, `unwalkable`, `unreadable` (each hides files the prune would then read as stale) and a scan that found nothing at all, which needs no failure to reach: a nested library scanned without `-r`, or one whose containers are outside `--extensions`, resolves cleanly and would take the whole cache with it. `unresolved_excludes` is deliberately not an obstacle — a failed `-e` makes the scan WIDER than asked, so the prune removes less than it could, which costs nothing. What this cannot catch is a scan that is incomplete without saying so — a non-recursive walk that finds *some* files still prunes the subfolders it never looked in, and that is the flag working as documented. The skip is `stats.cache_prune_skipped`, a problem rather than a skip for the same reason `clustering_abandoned` is: the user asked for a prune and did not get one.

**A compaction is decided by what the prune REMOVED, not by the flag that asked for one.** Emptying a table frees its pages inside the file but does not shrink the file, so `Database::compact` is the only thing that hands that space back to the filesystem — and it does it by copying every live page into a fresh file and fsyncing, which on a large cache is the most expensive thing a warm run does. It runs once, in `main`, after `run` has returned, and it is gated on `stats.entries_pruned() > 0`. Not on `args.prune_cache`, which is what it used to read: that flag is a REQUEST, and there are four ways a run can decline it after taking one. `--clear-cache` beside it skips the prune outright (after a clear nothing is stale because there is nothing at all, and the clear already compacted while the file was empty). `prune_obstacle` refuses a scan that fell short — the visible bug, which printed "Not pruning the cache: 1 scan path(s) could not be resolved" and "Compacted the fingerprint cache." one after the other, a full rewrite plus an fsync to reclaim exactly nothing. A prune with nothing stale in front of it removes nothing either. And `run` can fail before it ever reaches the prune, since the compaction sits ABOVE the `outcome?` that returns the error. `RunStats::cache_entries_pruned` is what the condition reads, counting removals from both tables, and it is deliberately in neither the problems list nor the skips: it is never printed and does not touch the exit code, and it exists only because the decision is taken in a different function from the removal. Erring toward not compacting is the cheap direction — space not reclaimed is space the next prune hands back, where a compaction taken is a rewrite the user waits for now. `test_a_prune_that_removed_nothing_leaves_nothing_to_compact` drives all three prune outcomes over one cache. Compaction is skipped after an interrupt as well, for a separate reason: the user asked for this to stop, and rewriting the database is the opposite of stopping.

**Failures are remembered too, in a table of their own, and that separation is the whole design.** `REFUSED_TABLE` holds one entry per file this build looked at and would not fingerprint — keyed by path, guarded by the same `Stamp`, and holding a `Refusal` (`NotMedia`, two numbers the sentence is regenerated from; `Said`, the message the run printed; or `TooShort`, which is a measurement rather than a verdict — see the `--min-duration` invariant below). It is a SECOND table rather than a new value shape in `CACHE_TABLE`, which is why it cost no rename and no re-decode, and it is what makes `-x '*'` usable: a cold scan of a 248k-file home directory is ~3 minutes and a warm one **7.5 s**, where before this it was 24 s and before any of this work it never finished at all. It costs ~135 MB of cache for that directory, and `--prune-cache` collects both tables (the refusals are the half that grows without bound — one entry per file that is not video).

`SUPERSEDED_REFUSAL_TABLES` is a second list beside `SUPERSEDED_TABLES` rather than more entries in it, because what a retirement COSTS is not comparable between them and the run says so in different words: dropping a fingerprint table promises a re-decode of the whole library, dropping a refusals table promises a re-probe measured in seconds. Telling a user with a large library that "fingerprints will be rebuilt" when only refusals went is telling them to expect an hour that is not coming.

**The two halves are retired on opposite schedules, on purpose.** A fingerprint is expensive to rebuild, so `Stamp` guards it as tightly as it can and `CACHE_TABLE` is renamed only when a field changes meaning. A refusal is worth half a millisecond, so it is discarded on the merest suspicion — and it has to be, because it depends on things `Stamp` deliberately does not record: the vendored FFmpeg's demuxer set and this tool's own probe gate. The name carries both (`refused_ff8_probe3`); change `FIRST_PROBE_BYTES`, `SECOND_PROBE_BYTES`, `NO_EVIDENCE`, what a `NotMedia` counts, or the FFmpeg major, and you must bump the suffix and push the old name into `SUPERSEDED_REFUSAL_TABLES` — not `SUPERSEDED_TABLES`, which would tell the user their fingerprints are being rebuilt — or files that would now read as video stay remembered as junk. That costs one cheap re-probe of the library and nothing else. `refused_ff8_probe2` was retired for the narrowest reason on that list: `NotMedia::bytes` was the probe size the gate reached and is now that size capped by what the file holds, so an old entry regenerates "no demuxer recognised the first 16384 bytes" for a file with nothing in it.

**What may be remembered is decided by `worth_remembering`, and the errno list in `is_transient` is the load-bearing part.** A failure is cached unless it is about the moment rather than the file — a permission, a vanished file, a dropped mount — because only those can legitimately answer differently next run with the bytes unchanged. The test is the error's type and errno, never its text: `ffmpeg_next::Error` maps known AVERRORs to named variants and the `AVERROR(errno)` family to `Other`. The first version tested "has an errno at all" and was wrong in a way only the corpus showed — `AVERROR(EINVAL)` is how libavformat reports plenty of ordinary content problems, and 746 files in that home directory fail that way, so all 746 were re-opened and re-decoded every run. `ENVIRONMENTAL` is therefore an explicit list, EINVAL is deliberately not in it, and the default for anything unlisted is that the failure is about the file. Getting this wrong in the other direction is the one that matters: a transient failure remembered is a file skipped until it changes.

**Both refusal writes are batched into one transaction**, unlike `cache_store`, which commits per video. A decode costs seconds and an interrupt must not throw one away; a refusal costs half a millisecond and there can be a quarter of a million in one run, so one fsync each would cost far more than simply re-probing next time. Losing the lot to an interrupt is the correct trade.

**Cache correctness is enforced by the table name.** `CACHE_TABLE` in `main.rs` is currently `fingerprints_dct_ct_ff8_kffloor`; `SUPERSEDED_TABLES` lists the dead ones, dropped whole on first run. Appending a field to the end of `VideoFingerprint` is self-invalidating — old entries run out of bytes and bincode fails cleanly. **Changing what an existing field *means* (units, clock, hash algorithm) is not caught by anything**, so it requires renaming `CACHE_TABLE` and pushing the old name into `SUPERSEDED_TABLES`. Read the comment above those constants; each past rename records the bug that forced it.

The `_kffloor` suffix is the most recent rename, and it is the narrowest one on the list: it retires only the entries a run typing `--keyframe-interval N --min-keyframes 0` (or a negative, or NaN) wrote. `--min-keyframes` is a FLOOR on the interval, so a floor of nothing leaves the interval standing — it used to drop the interval as well and decode every keyframe, which is the one reading of the flag under which asking for a wider interval AND fewer minimum samples adds up to a request for all of them (see the min-keyframes invariant below). The stamp records `kf_interval = N` either way, so those every-keyframe entries match a new run's stamp exactly and would be handed back with roughly N times too many hashes. A cache that never saw that flag pair holds nothing wrong, which is the argument for not renaming — and there is no bit in the `Stamp` that separates the two, which is the only test that has ever decided it. Nothing else moves: default runs are untouched and the local accuracy harness passes unchanged on all three profiles after the forced re-decode.

The `_rescale` suffix before it retires a fingerprint that stops part way through a file for a reason entirely separate from the one below. The scaler was built from the first frame the decoder produced and never rebuilt, and libswscale refuses outright any frame that is not the shape its context was built for — so a stream that changes resolution or pixel format mid-file returned `Error::InputChanged` on every frame after the change, both call sites discarded it, and the file simply stopped being sampled there (see the rescale invariant below). No clock restart is needed to reach it: a broadcaster switching feeds, a camcorder dropping to a lower mode, or `cat` of two encodes at different sizes is enough, and the `Stamp` cannot tell such an entry from a good one. The 756-file local corpus reports byte-identical CSVs across the change on all three accuracy profiles — none of its files rescale — which is again the argument FOR the rename rather than against it.

The `_splice` suffix before it was the same shape of damage by the other route: it moves nothing at all on a file whose container counts forwards, and holds half a file for one that does not. A capture built by concatenating two recordings restarts its timestamps at the join, and both halves of the demux loop navigated by them — so `cat s1.ts s2.ts > capture.ts` was fingerprinted as `s1.ts` and cached that way (see the splice invariant below). The `Stamp` cannot tell such an entry from a good one: it matches its file's mtime and size exactly. The 756-file local corpus reports byte-identical CSVs across the change at `-d 4 -p 20`, which is the argument FOR the rename rather than against it — nothing a layout check or an accuracy run can see is what a rename is for.

The `_tail` suffix before it was the cheapest kind: `sample_times` divided the span of a video by its sample *count* rather than by the number of gaps between the samples when extending the last sample, so `total_ms` came out a few tenths of a percent short. Same field, same units, different value — which is exactly what a layout check cannot see. It fires whenever the samples outrun the runtime the container reported, not merely when there is no runtime at all (an MP4 opening on a negative dts gets there, because anchoring at the first keyframe shifts every sample later); three of the 727 files in the local corpus hit it. No grouping decision moved on any of the three accuracy profiles, so that rename cost a re-decode and nothing else.

**The vendored FFmpeg version is one of those meanings.** The `_ff8` suffix names the rename before that: decoder output is not bit-identical across FFmpeg majors, and the `Stamp` records mtime, size and the sampling knobs but deliberately *not* an FFmpeg version — so entries written either side of a version change are indistinguishable to a lookup. Bumping `FFMPEG_VERSION` in `scripts/build-ffmpeg-static.sh` across a major therefore costs a `CACHE_TABLE` rename and a re-taken accuracy baseline, exactly like changing the hash algorithm would. It is not a routine dependency bump.

**What belongs in the cache `Stamp`.** mtime (with nsec), size, and the sampling knobs (`--keyframe-interval`, `--min-keyframes`) — anything that changes *which frames get hashed*. Thread count is excluded on purpose (it changes only speed); the claim that it changes nothing else is checked by `test_threaded_decode_is_bit_identical` and holds over the whole corpus. `-d`, `-p` and `--min-duration` are comparison-time and must never enter the stamp.

`Stamp::matches` compares `min_kf_samples` only when `sampling_is_on(kf_interval)`, because that flag is a *floor on the interval* and with no interval there is nothing to floor — see `effective_interval`, which will not read it either. And it compares it through `same_floor` rather than `same_setting`, for the same reason `same_sampling` exists one rung up: `effective_interval` computes the floor only when `min_kf_samples > 0.0`, so 0, any negative and NaN all mean *no floor* and produce identical fingerprints, and none of them may invalidate another's entry. It is still written into every stamp, so the struct layout (and therefore the byte offset the fingerprint begins at) is unchanged and existing caches keep hitting.

**Both sampling knobs are refused out of range, on the same terms as `-d`, `-p` and `--min-duration`, and for a reason those three do not have.** `effective_interval` asks `kf_interval > 0.0` and `min_kf_samples > 0.0`, so a negative, an infinity or a NaN is not an out-of-range setting at all — it is silently the DEFAULT. `--keyframe-interval=-5` decoded every keyframe in the library and printed nothing about it, because the "Using keyframe interval" line is gated on the same test, so the run cost what a full-rate scan costs and reported what a full-rate scan reports with nothing anywhere connecting either to the flag. 0 stays legal in both and is documented (it turns the interval off; it removes the floor). `Stamp::same_sampling` and `same_floor` still treat every one of those values as "off" and must keep doing so — caches written by builds that accepted them are still out there, and an entry written with a negative interval holds exactly the fingerprint a default run wants.

**`--min-keyframes` is not monotone, and its default of 12 was measured rather than guessed.** Coverage is the span each hash stands for, so a denser sample makes every hash stand for less; extra samples that match nothing dilute a pair's coverage percentage and can push it back under `-p`, taking a pair OUT of the report. This is not a small effect and it is not noise: swept over `--keyframe-interval` 5/13/21/29 at the default `-d 4 -p 20`, F1 on the labeled pairs peaks at `-m` 4, 12, 20 and 28 and collapses at 8 and 16 (AN 0.791 at 6 → 0.744 at 8; Wire 0.829 → 0.526). Re-running the dip at `-p 0` proves the mechanism: on Wire at `-i 21`, **all 64** of the pairs `-m 8` loses are found with the gate off, and there the two settings are identical (406 pairs, same P and R). The old default of 4 sat on a safe rung but left a lot behind — 12 takes combined F1 across the two corpora from 0.847 to 0.918 for 9.4% more wall time, and it is the best rung on the long-video corpus outright.

The reason it is that cheap is that `effective_interval` is `min(kf_interval, duration / min_kf_samples)`, so the floor only reaches a file whose runtime is under `kf_interval × min_kf_samples`; at `min_kf_samples <= 0` there is no floor at all and the interval applies at every length. **That setting is measured and it is a bad one on a short-clip corpus**, which is the point of having fixed it: scored on `benchmark/labels.csv` at `-d 4 -p 20`, `-m 0` takes recall (SAME) from the default run's 75.4% to 45.4% at `-i 5`, 46.5% at `-i 10` and 23.1% at `-i 15`, because with no floor the median file keeps 2, 1 and 1 samples and 40/59/65% of reported files are down to a single hash — which can never be corroborated, so it is held to `strict`. Precision stays at 100% at every rung (the corpus's one false positive goes with them), and four files fall out of `-i 15 -m 0` entirely with "No usable frames": their lone kept keyframe is featureless, so it is dropped below `MIN_AC_ENERGY` and nothing is left. All of that is loud — named, counted, exit 2. Before the fix those three cells reported pair sets IDENTICAL to a default run and cost 125-127 s against 29-61 s, which is the whole bug in one line: the interval was discarded and the time was spent anyway. At the default `-m 12` the reports are identical either side of the fix at `-i 5`, `-i 10`, `-i 15` and `-i 0`. A 59-minute episode is sampled at the flat interval whatever this flag says: over the whole `-m` 1→28 range the Wire folder moves 22.2 s → 23.7 s, against 25.8 s → 37.4 s on the short-clip corpus. Anyone re-tuning this must say which `-p` they measured at, because the flag's whole shape comes from that interaction. The harness is `benchmark/kf_sweep.py` and `benchmark/kf_report.py` (the latter takes `--only-under` to score a subfolder scan against just the labels it could reach).

**Decoder threads are apportioned by measured decode cost, not by file count and no longer by bytes** (`share_for`, `ThreadBudget`). FFmpeg fixes a decoder's thread count when it is opened, so a heavyweight must be given its share at the moment it starts or never — hence the heaviest-first sort, the atomic cursor instead of rayon (rayon's splitting breaks that ordering), and the blocking claim in `claim_next`. A `Grant` releases its threads on drop, including on error and Ctrl-C.

**Drawing the next video and reserving its share are one operation** (`ThreadBudget::claim_next`), and that is what makes the heaviest-first ordering real rather than intended. The cursor and the ledger used to be taken in sequence, leaving a window in which any lighter worker could reserve first — so the heavyweight was priced against a budget and a queue somebody else had already moved, in either direction. That ordering is worth 12% of wall time on the 41-file 54 GB scan `share_for` records, and the window put it up to chance. Nothing was ever over-committed by it (the ledger is still one lock and a `Grant` is still the only way to hold threads), so it cost wall time and not correctness, and only at worker start-up, which is the one moment every worker is racing. `test_the_heaviest_video_is_still_first_when_every_worker_starts_at_once` pins it, and needs a barrier to do it: thread spawning is sequential enough that worker one is usually finished before worker two exists. The wait now takes the queue as well, so a worker blocked on a fully-committed budget with nothing left to claim gives up instead of waiting for a decode to finish only to draw an index past the end.

**The weight itself comes from `fingerprint::weigh_decode`, and the unit is keyframe-pixels.** ~93% of fingerprinting time is intra decode of the keyframes, so the honest weight is how many of them there are times how big they are; the file's size only tracks that through bitrate, which is why a well-compressed 4K file used to be scheduled behind a bloated SD one. The keyframe count is not estimated — it is counted out of the container's own index, which MP4 and AVI build while reading the header and which Matroska will build if you ask it for a seek (80–250 µs; the count equalled the keyframes actually decoded on all 753 files measured). Measured against single-threaded decode time on the files big enough to time, that halves the median error against the old byte weight (21% vs 46%) and cuts the 10th-to-90th-percentile spread from 5.5× to 2.2×. Everything after that is a ladder of fallbacks — assumed 4 s keyframe spacing when there is no index, then `WORK_PER_BYTE` when the container opens but will not say anything useful — because a file that cannot be MEASURED still has to be scheduled.

**A file that will not decode is a verdict from this pass, not the bottom rung of that ladder.** `weigh_decode` returns `Weighed::Undecodable(e)` carrying the error `fingerprint_video` would have raised, and `run` logs it, counts it in `fingerprint_failed` and drops it from `todo` — so nothing opens it a second time. Only three routes produce one, and each is a point the decode provably reaches on the same file: `open_input` fails (its own first call), the probe fails (run here only when the header did not answer, which is exactly when `header_is_complete` is false, so the decode probes too), or the probe succeeds and there is still no video stream. That correspondence is the whole safety argument — a fourth route would report a file as broken without anything having tried to read it — and `test_the_weigher_and_the_decoder_agree_about_a_file_that_is_not_video` pins it by running both halves on one file and comparing the sentences. This is also why `probe_streams` is one function with two callers rather than two copies of `avformat_find_stream_info`.

**The other verdict from that pass is `--min-duration`, and the thing the cache keeps for it is a runtime rather than a skip.** A file under the floor is never fingerprinted, so it writes nothing to `CACHE_TABLE` and was a miss on every run for ever — and it paid for that miss twice, because the weighing pass opened it to price a decode that was then opened again only to read the same header and give up. Measured with `strace -e openat` over 60 short files, opens of one of them: 4 cold and 0 warm with the flag off, 4 cold and **4 warm** with `--min-duration 60`. It is now 2 cold and 0 warm, and a warm scan of 500 such files went 0.08 s → 0.02 s.

`weigh_from_container` answers it, and only from a header `header_is_complete` vouches for — which is exactly the condition under which `fingerprint_video` does NOT probe, so both passes read the same `duration_seconds` of the same stream and reach the same conclusion. That is the same correspondence argument the paragraph above rests on, and it is why the question is not asked at all of a header that is short of anything: a probe can move the runtime, and the direction that matters is the one where this pass drops a file the decode would have kept. `test_the_weigher_and_the_decoder_agree_about_a_file_that_is_too_short` pins it as a bracket — a floor either side of the reported runtime has to move both passes the same way — rather than as a float comparison between the two.

**What is remembered is `Refusal::TooShort(duration)`, the number, because "too short" is not a fact about the file.** `--min-duration` is comparison-time and is kept out of the `Stamp` along with `-d` and `-p`, so a remembered VERDICT would hand a later run that lowered the flag a skip it never asked for, and there is no bit in the stamp that would catch it. The runtime is a fact about the file, guarded by the stamp like everything else in that table, and each run re-decides from it in the cache pass (`Lookup::Short`) without opening anything: too short for this run's floor is a skip, long enough is an ordinary miss that goes on to decode. Only the weighing pass writes one — the decode's own `Ok(None)` still just counts the skip, because a file that gets that far had a header nothing could vouch for. The variant is appended last so bincode's variant numbering leaves the two above it alone and caches written before it are still read; it is a skip and never a problem, so nothing about the exit code moves.

It is also the one entry `CACHE_TABLE` can supersede, and `cache_store` removes it in the same transaction as the insert. Falling through is the whole point of storing a number, and the run that falls through DECODES the file, filing a fingerprint under the path the refusal is under — so `--min-duration 60` followed by `--min-duration 0` used to leave the path in both tables at once, which is the shape the two-table design says cannot happen (`cache_forget` reasons from it out loud). Neither entry is stale, so nothing collects it and no `Stamp` could catch it; only `--prune-cache` after the file itself moves away, which is how it shows: one removed path counted as one stale entry AND one stale refusal. The wrong direction is that `Lookup::Short` answers before `cache_lookup` is reached, so the header runtime the weighing pass measured outranks the runtime the decode went on to measure, permanently. Those two differ only for a file that restarts its clock — `fingerprint_video` takes the runtime from the samples there, and it is longer — which today cannot also be `header_is_complete` and so cannot also carry a `TooShort`, making it latent rather than visible. Removing the refusal where the fingerprint is written, rather than where the fall-through happens, is what makes "one path, one table" true by construction.

**`open_input` refuses a file no demuxer recognises, before libavformat opens it.** This is the single largest cost in a `-x '*'` scan and it is spent entirely on proving negatives. `av_probe_input_buffer2` doubles its probe buffer — 2 KB, 4 KB, … to 1 MB — for as long as nothing has scored above `AVPROBE_SCORE_RETRY`, re-running all ~300 demuxer probes at every step; for a file that is not media that loop always runs to the end. Measured over the 248k files of a home directory: 0.5 ms at 4 KB, 24 ms at 64 KB, 130 ms at 512 KB, flat at ~140 ms above 1 MB — **2,042 s of the 2,099 s that scan spent weighing, 97% of the pass**, almost all of it about `.o` files. So `unrecognised` runs libavformat's own first pass itself (`FIRST_PROBE_BYTES` = `PROBE_BUF_MIN`, so it is not a new question, just an earlier reading of the same one) and stops there when the answer is nothing. Weighing went 2,099 s → 149 s of CPU, 14x, and the whole cold scan 552 s → 213 s.

Two constants carry the safety argument, and both are measured rather than chosen. `NO_EVIDENCE = 1` is the score libavformat assigns when it has none: `av_probe_input_format3` floors at 1 the score of a demuxer that has a `read_probe` and whose extension list matches the NAME, whatever the bytes said, and `mp3_probe` returns 1 for a single frame sync anywhere in the buffer. **That floor is also what makes the gate hard to get wrong — a file named like media always scores at least 1, so it can never be refused on the first reading.** It is only ever exactly 1 for a demuxer that brought a probe of its own and got nothing out of the bytes; one with an extension list and no `read_probe` scores `AVPROBE_SCORE_EXTENSION` (50) on the name alone, and an extension match over an ID3 tag too long for the buffer floors at 24 or 50. Every one of those clears the line, which is why the rule can be stated as the floor. `SECOND_PROBE_BYTES = 16384` is where those go: a real 11.8 MB MP3 in that corpus scores 1 at 2 KB, 25 at 4 KB and 51 from 8 KB on, because its first frames sit behind an ID3 tag, and refusing it on the 2 KB reading was wrong even though nothing downstream would have fingerprinted it. Of the 3,404 files a full 1 MB probe identified with a real score, 40 fall below this line: 39 are object files and build caches that a big buffer briefly reads as `mpegvideo` (a score that goes 51, then 0, as the buffer grows again), and the fortieth is that MP3, which the second look recovers. Not one file with a media extension is turned away, and every one of the 735 real videos in the two test corpora scores 98 or 100 at 2 KB — the margin is not a few points, it is the whole scale. The accuracy baselines are byte-identical across the change.

The case it was written for is `-x '*'` over a folder that is mostly not video: 229k files, an open each, every one of them opened twice — once to be weighed, once for the decode to discover the same thing — and then charged `size × WORK_PER_BYTE` on a progress bar they finished the instant they were looked at. Five 20 MB junk files took 71% of that bar while three real videos, the whole run, shared the rest; the bar sat at 100% for minutes with nothing to print. Measured on 4,000 files of noise, that run went 4.2 s → 1.9 s, and the bar now covers only files that are really going to decode. It did not originally remember the verdict between runs, so a second scan paid the same quarter of a million opens as the first (24 s warm on that tree); `REFUSED_TABLE` is what fixed that, and it took a second table rather than a new value shape in `CACHE_TABLE` precisely so it cost no rename and no re-decode.

**The two sizes are read lazily, and the buffer belongs to the worker.** Only the ~9% of files that score exactly `NO_EVIDENCE` at 2 KB are read to 16 KB, out of the handle the first stage left open, so a `-x '*'` scan of the build tree reads 58 MB where it used to read 108 MB (15,915 files, 1,441 of them reaching the second size). The buffer is one thread-local `Vec` grown once per decode worker rather than a freshly zeroed 16,416-byte allocation per file. **None of that is why it was done** — measured over the whole 145,904-file tree with a fresh cache, four interleaved runs each, wall time is 12.2-13.7 s before and 12.2-13.4 s after, which is noise. What it buys is the padding: `probe_head` used to be handed `len = 2048` over a buffer already holding all 16 KB, so the 32 bytes past the probe window were the file's own data where `av_probe_input_buffer2` memsets zeros before every one of its own probes, and a demuxer that reads into its padding was answering a question libavformat never asks. Reading 2 KB and zeroing behind them makes the first reading exactly the reading libavformat is about to compute, which is what the whole gate rests on. No file on this machine changed its verdict — 98,209 files across the build tree and both video corpora were probed both ways and every score agreed, and a full `-x '*'` scan of the tree is byte-identical in report, stdout and every refusal sentence — so `refused_ff8_probe3` was retired on suspicion rather than on a measured difference. `test_every_probe_reading_is_padded_with_zeros_and_not_with_leftovers` pins both ways of getting it wrong (the first reading's padding is where the second reading's bytes land; the second's is where the previous FILE's bytes are still sitting), and `test_only_a_file_that_showed_a_whisper_is_read_past_the_first_probe` pins that the second read is paid for only by the files that earned it.

The cost of it is one `avformat_open_input` per file, **paid only on cache misses**: the weighing pass sits after the cache pass, so a re-run over a warm cache pays nothing. That placement is also why `sources::collect`'s size sort is now only an approximation of the real order — `todo` is re-sorted on the measured weight once the pass has run.

**A demuxer that will not say EOF must not be asked forever, and one of them does not.** The demux loop treats a failed `packet.read` as a packet to skip rather than the end of the video, which is right for a corrupt frame mid-file and is an infinite loop at the end of one: `ncdec.c` ends `while (state != NC_VIDEO_FLAG) { if (avio_feof(pb)) return AVERROR_INVALIDDATA; … }`, so at EOF it reports invalid data, is asked again, reports it again, forever. `AVERROR_EOF` is a convention, not a guarantee. The `nc` demuxer claims any file named `*.v` on an extension match alone, so a 132-byte linker version script — `libavcodec.v`, one per FFmpeg build directory — probes as an mpeg4 video of unspecified size and spins one core until the process is killed. **That is the hang: 80 minutes, 707% CPU, 2.9 MB RSS, eight decode workers each stuck on one of eight such files, no output at all.** It is what made `vid-fp DIR -x '*'` over a home directory never finish. The loop now ends on `input_is_spent` (`avio_feof`, the byte-level truth) or after `MAX_CONSECUTIVE_DEMUX_ERRORS` = 1024 consecutive failures, which covers the same shape mid-file where `feof` is not yet true; both are ordinary ends of stream, so the file keeps whatever frames it gave up and the existing "no frames" path reports it if that is none. `test_a_demuxer_that_cries_invalid_data_at_eof_does_not_spin_forever` builds the four bytes that reproduce it and runs the decode under a deadline, so losing the guard fails in ten seconds instead of hanging the suite. The probe gate above now refuses that particular file earlier, which is a second line rather than a replacement: the gate is about names and magic bytes, and this is about a loop that must terminate whatever gets into it.

**A container is allowed to restart its clock, and timestamps are then no guide to what is further into the file.** `cat s1.ts s2.ts > capture.ts` is how a DVB capture, a camcorder split and a rescued recording are laid out, and the second segment reuses the first one's timestamps — which is why `.ts`, `.mts` and `.m2ts` are in `DEFAULT_EXTENSIONS` in the first place. Every part of the demux loop that read the clock as a map of the file got this wrong, and the result was **half a video, silently**: `capture.ts` fingerprinted as `s1.ts`, with `s1.ts`'s hashes and `s1.ts`'s runtime, exit code 0, nothing in the problem summary, and the truncated fingerprint cached for every run after. It is worse than a missed match. A file that CONTAINS another read as the same length as it, lost the ranking on encoder quality, and was the one marked **DELETE** — the "length protects the host" property the DELETE rule leans on, defeated by a runtime the container itself got wrong (last timestamp minus first, which across a splice is one segment).

Three things fix it, and they are three different questions:

- **The dedup guard is asked only after a seek** (`after_seek`). It exists to catch a seek landing on a keyframe already decoded, and asked of every keyframe it reads a clock restart as a seek that keeps landing short. On a two-segment mpeg-ps capture the demuxer handed over all ten keyframes — five of them read linearly, one after another, past a join the seek had already crossed — and the guard threw the last five away for carrying timestamps the first segment had used.
- **A container libavformat marks `AVFMT_TS_DISCONT` never enters the seek path** (`clock_may_restart`, `seeking_broken` starts true). That flag is the demuxer's own declaration that its timestamps need not run forwards, and it is set on exactly the two families that can be built with `cat` — MPEG-TS and MPEG-PS — and clear on MP4, Matroska, AVI and ASF, which have to be remuxed. What a timestamp seek does wrong varies with the demuxer and is not worth detecting: on the `.ts` build of one spliced file a forward seek binary-searched its way into the MIDDLE of the second segment (three of six keyframes read, two never looked at), and on the mpeg-ps build of the same content it ran off the end and reported EOF. **It costs nothing**: measured on a 228 MB, 15-minute `.ts`, both paths read the whole file (465,464 blocks, byte for byte the same) and both take 1.2 s, because MPEG-TS seeking is a binary search over the same bytes. The seek path was written for Matroska, which is untouched.
- **The sample clock accumulates gaps instead of subtracting an anchor.** A restart is charged the last gap the file showed — an estimate, and the only one available — so the times only ever go forwards. For a file whose clock does run forwards this is `ts - first_key_ts` term by term, which is why the local corpus is byte-identical either side. The runtime is then taken from the samples when they outrun the header, but **only for a file seen to restart its clock**, so no rounded duration moves and `total_ms >= duration * 1000` still holds. What still reads the header's figure is everything that runs BEFORE the decode — `--min-duration` and `weigh_decode` — because at that point the file has not been walked and there is nothing better to read.

`test_a_clock_that_restarts_mid_file_does_not_truncate_the_fingerprint` doubles a 3-keyframe `.ts` fixture and demands the whole of its fingerprint twice on an ascending clock; on the old code it reports 3 hashes where 6 are due. `test_only_the_containers_that_can_be_spliced_are_kept_out_of_the_seek_path` pins the flag, because the whole argument rests on which containers it is set for.

**A stream is allowed to change shape mid-file, and the scaler has to be rebuilt when it does.** This is the second route to the same half-a-video the splice invariant above describes, and it needs no clock restart at all — a broadcaster switching feeds, a camcorder dropping to a lower mode, an encode of two sources concatenated, or one `cat` of two files at different sizes. The scaler was built from the first frame the decoder produced and never rebuilt; `Context::run` compares the frame's format, width and height against the context's own `input()` definition and returns `Error::InputChanged` outright when they differ, and **both call sites discarded the result** (`let _ = process_frame(&decoded);`). So from the change onwards every frame was dropped before `frame_idx` was even incremented: no sample, no count, nothing logged, exit code 0, and the truncated fingerprint cached for every run after. `process_frame` now compares against `scaler.input()` — the context's own record, so there is no second copy to drift — and rebuilds when it differs.

Two decisions fall out of it. The reported `width`/`height` stay the FIRST frame's (`frame_dims.get_or_insert`), because a file that rescales has no one true answer, that is what the header would have said, and it means no file's reported resolution moves because of the fix — which is what keeps the ranking untouched. And a frame that still cannot be scaled now **fails the file** rather than being dropped, because returning short is the failure this whole invariant is about. The rebuild answers the one cause that is a normal property of a stream, so what is left is a pixel format libswscale will not take, which no single frame can have on its own — meaning it fires for a whole file or not at all. It is asked BEFORE the `frame_idx == 0` line so such a file says which of the two happened. Nothing in the 756-file local corpus reaches it: a full scan is exit 0 with an empty problem list, and all three accuracy profiles are byte-identical.

`test_a_stream_that_changes_resolution_mid_file_keeps_sampling` concatenates `test_video_segment.ts` with the same footage at 320x240 and demands six hashes where the old code gives three, then checks the second half's hashes against the first half's within 3 sigma — because a count alone would also pass on a scaler that emitted garbage.

**A video with no picture in it is a failure, not a fingerprint holding nothing.** This is the third route to a fingerprint that describes less than the file, and the most complete one: `is_featureless` drops a frame whose AC energy is below `MIN_AC_ENERGY` so a fade or a title card cannot link two unrelated files, and the only guard on the result was `frame_idx == 0` — which counts frames the DECODER produced, never hashes that survived the filter. So a file whose every frame is blank returned a `VideoFingerprint` with an empty hash list. It was cached like any other, it matched nothing at any tolerance, and **two byte-identical all-black recordings reported zero groups at `-d 32 -p 0`, exit 0, with an empty problem list** — a run that had decoded both files and had nothing to say about either. Worse warm than cold: the empty entry carries the right `Stamp` for its file, so no later run re-decodes it and no setting the user can reach makes the tool say what it found.

`final_hashes.is_empty()` is now the same kind of refusal as the unscalable frame above it, and deliberately a different sentence — "it decoded and there was nothing in the picture" is a different finding from "it decoded nothing", and it is the sentence `Refusal::Said` remembers, so a re-run replays it without opening the file. Reachable from any all-black or all-noise capture, and from `--keyframe-interval` thinning a short file down to a single keyframe that happens to be blank.

The entries an older build already wrote are handled in `cache_lookup` rather than by a `CACHE_TABLE` rename: an entry with no hashes reads as a MISS, so the file is decoded once more and fails loudly, and `REFUSED_TABLE` covers every run after that. The rename would have been the usual answer to a stored value that is wrong — but this one is wrong in the direction that can only ever LOSE a match, never make a bad DELETE, and it would have charged every user a re-decode of their whole library for a handful of blank videos. Emptiness is the whole tell there is, since nothing about such a file changed; no fresh entry can be empty. The 756-file local corpus is byte-identical on all three accuracy profiles across both halves.

**Memory is deliberately flat across a run.** Frames live in one contiguous `FRAME_STRIDE`-sized allocation per video so glibc serves it via mmap and returns it at once; `main()` pins the mmap/trim thresholds with `mallopt` to stop dynamic growth undoing that. Don't replace the frame buffer with a `Vec<Vec<u8>>`.

**Phase 2's list of loose frame matches is the other thing that could undo that, and it is bounded as a working set rather than by a ceiling** (`MAX_ALIGNED_MATCHES`, `corroborate_pair`). Everything else that stage allocates is sized by the number of SAMPLES; this holds one 24-byte entry per matching frame PAIR, so it is `|A| × |B|` when every sample of one video matches every sample of the other — which is what a static camera produces, not a contrived input. Two 2-hour recordings of one lecture are 4,000 samples each and 16 million matches: **372 MB for a single pair**, on a stage that runs one pair per rayon worker. Past a million entries the pair is corroborated in bands of the time-offset axis instead, one band held at a time. Corroboration is local in that axis — a witness has to sit within `ALIGNMENT_TOLERANCE_MS` — so a band carrying a skirt of that width on each side sees every witness the whole list would have offered and **the verdict is identical**; a ceiling, by contrast, would have had to throw matches away, which is a wrong answer rather than a refused one. The cost is one more sweep of the quadratic compare per band, paid only by pairs that were already the most expensive thing in the program: 16,000,000 entries held becomes 1,051,365 for 2.5% more time on that pair. Nothing in the local corpus comes close to the cap (the whole list is +0.6 MB of peak RSS at `-d 4`, +2.4 MB at `-d 24`) and its reports are byte-identical at `-d 4` and `-d 18` either side of the change. `test_cutting_the_offset_axis_into_bands_changes_no_verdict` is the guard, and it is written so that dropping the skirt fails it: every match in it has exactly one witness, 120 ms away, and with a one-match cap every bucket boundary is a band edge.

**DELETE always rests on a direct measurement, and the clique rule is what enforces it.** A file marked DELETE lost the ranking inside a group whose members were all compared with each other, so it was compared with the file that beat it. Nothing in `export.rs` re-checks this — it does not have to, and the guard it used to carry (`matches.coverage(idx, s).is_some()`, plus a `--trust-chains` flag to switch it off) was removed when grouping went back to cliques, because a complete subgraph makes it unfalsifiable. **Loosen the clustering rule and that guard has to come back with it.**

**Clique enumeration is bounded per component, and a component that outruns its bounds is dropped whole.** Maximal-clique enumeration is 3^(n/3) in the worst case and the worst case is reachable from the command line — unrelated hashes sit ~32 bits apart, so a loose `-d` over a large library is a near-complete graph by construction. Measured on the 756-file local corpus, groups by `-d`: 141 at 8, 232 at 12, 574 at 14, 1,891 at 16, **9,003 at 18, 139,025 at 20** (52 s, 1.4 GB RSS, a 2.6-million-row CSV), and at `-d 22` the old build was still going after 5 minutes capped at 1.5 GB. That is the hang, and it is two rungs past a setting that still works.

Two ceilings stop it, both per connected component and both in `Ceilings`: `SEARCH_BUDGET_PER_COMPONENT` (50M set probes, charged per set operation by `Search::spend`) and `MAX_GROUPS_PER_COMPONENT` (100k cliques). The budget is one number covering three failure modes: a probe is a hash lookup, so time is counted directly; the sets a step holds are never larger than the work it does on them, so the heap follows (177 MB at `-d 24`, 562 MB at `-d 32`); and depth follows too, because a clique of `d` members costs ~`3d^2 / 2` probes, which caps recursion at ~5,800 frames. That depth is given a stack of its own (`SEARCH_STACK_BYTES`, 64 MB of address space on a scoped thread) so the bound is this program's rather than whatever `ulimit -s` happens to be — a complete component of 4,000 files needs more than the 2 MB a rayon worker gets. Where exactly the group ceiling sits barely matters — this corpus goes 9k → 139k → uncountable across two rungs of `-d`, so anything from 20k to 200k cuts in the same place. Results are **byte-identical to the pre-ceiling build at `-d 4, 8, 12, 14, 16, 18`**, and it bails in 1-7 s from `-d 20` up.

**The budget charges what the search really spends, and that proportionality is the whole ceiling.** `HashSet::intersection` walks the smaller side, so one candidate costs `min(deg(v), |p|)` probes rather than one (`intersection_cost`). The first version charged `|p| + |x|` per step and undercounted a dense component by a factor of `|p|`; the case that exposed it was a *nearly complete* graph, which has few enough maximal cliques to slip under the group ceiling while every step carries hundreds of thousands of probes. `-d 40` on the local corpus ran **eleven minutes single-threaded, still climbing, with neither ceiling firing** — the exact failure the ceilings existed to prevent, one rung outside where they were tested. Do not replace this with a flat per-step charge: it has to stay proportional to the work, or it stops bounding anything on the graphs that matter. Measured probes for the largest component: 5.4k at `-d 4`, 5.6k at `-d 12`, 75k at `-d 16`, 1.03M at `-d 18` (a 48x margin under the budget), 11.2M at `-d 20` where the group ceiling fires first, and the full 50M at `-d 32`, where the graph is complete enough that not one clique finishes.

**`choose_pivot` stops walking the moment it can prove it has the best pivot, and that is what keeps the ceiling off the easiest input there is.** Any `u` in `p ∪ x` is a valid pivot; the maximum is only what makes the branching narrow. The walk therefore ends as soon as a candidate reaches the most anything still to come could reach, and `x` is walked FIRST so that ceiling is knowable: a candidate from `x` can cover the whole of `p`, one from `p` is never its own neighbour and tops out one short. The pivot is still exactly the one the exhaustive walk chose. What it fixes is a ceiling firing hardest on the cheapest possible graph — a COMPLETE component has one maximal clique and one branch per level, but the old walk priced every candidate at every level anyway, so the search was `d^3 / 3` and anything past **~530** mutually-matching files was dropped whole, under a message advising a tighter `--hamming-distance` that cannot separate files which are identical. 600 copies of one video reported zero groups at `-d 0`, `-d 2` and `-d 4` alike. The walk is now one intersection per level on such a graph, the search `~3d^2 / 2`, and the reachable group size ~5,800. Reports are byte-identical either side on the local corpus at `-d 4, 12, 16, 18` (122/232/1891/9003 groups) and at `-d 20, 24, 32`, where both builds abandon the same two components in the same time.

**`-d` stops at chance (`compare::max_hamming_distance()` = 32), not at the width of the hash.** Two unrelated frames sit 32 bits apart on average, so at 32 half of all unrelated frame pairs already match and the flag has nothing left to control; above it the library is one group and, with `--delete` armed, one survivor. The old bound was 64 — refusing only the arithmetic that could not mean anything, and admitting a whole range that could not mean anything either. It is also the range where the clustering ceilings stop being enough on their own (the `-d 40` case above), so the cap and the budget are two independent answers to the same class of input; both are worth having, because the cap is about what the flag means and the budget is about what any input can cost. Stated as `sigma_below_chance(0.0)` for the same reason every other threshold here is in sigma.

Three properties worth keeping if you touch this. **Per component**, so one dense folder does not cost the user the groups in every other folder — a maximal clique never spans components, so this changes no result. **Dropped whole**, never partially: which cliques a truncated search found depends on `HashSet` iteration order, so reporting them would make the same library group differently run to run, and `--delete` would act on half a component's relationships. **Counted as a problem** (`stats.clustering_abandoned`), so the run exits 2 and says where the files are — this is the one case where raising `-d` takes files OUT of the report, which the README's monotonicity claim now says out loud. That line carries a count, which ceiling stopped it, and the deepest folder every member sits under (`common_parent`, compared a path component at a time so `/lib/season1` and `/lib/season2` share `/lib` rather than a `/lib/season` that does not exist). It used to name one member, the lowest path, chosen for reproducibility; a folder is what `--exclude` and a narrower scan take as an argument, it narrows by itself when one folder of a large library is the dense one, and a common prefix is stable without having to be chosen for it. The two ceilings deliberately say different numbers: the work budget reports how many groups it had found (0 means not one clique could be finished, a large number means it was enumerating fine and simply had more to do), while the group ceiling reports the THRESHOLD, because a search that stops the first time it exceeds a ceiling always holds exactly one more than it and printing that is printing the constant back. The recursion also polls `shutdown_requested()` on every step, which is what makes the "every stage polls it" claim above true; that path is deliberately not unit-tested, because the flag is process-global with no reset and setting it would leak into every test running beside it.

**`-t` is bounded by MEMORY, not by CPU time, and that is not what the flag looks like it controls.** Peak RSS is close to linear in `--threads` while throughput is flat. Measured with a fresh cache each run, so every file decodes — 100 720p clips: 5.2-5.4 s at every rung, 112 MB at `-t 8`, 205 at 16, 370 at 32, 620 at 64. 16 1080p clips: 5.2-5.5 s at every rung, 422 MB at 8, 647 at 16, 1,137 at 32, 2,022 at 64. That is ~9 MB per extra thread at 720p and ~28 MB at 1080p, so the slope is a property of the **library**, not of the machine, and 4K footage costs roughly four times the 1080p figure again. CPU utilisation is already 71-73% of eight cores at `-t 8`, which is why nothing above one worker per core buys wall time on local storage. Note the 1080p column keeps climbing past `-t 32` although 16 files cap the *worker* count at 16: the budget is what widens, so each decode is handed more decoder threads and each of those holds its own frame buffer. Both mechanisms scale with this one number, and it is the figure the `mallopt` calls and the single contiguous frame buffer exist to keep flat — an unbounded `-t` is the one input that undoes all of that.

**Thread creation is the cruder limit and bites two orders of magnitude later.** Timed on a warm two-file cache, so the pool is the whole cost: 0.02 s from `-t 8` through 256, 0.10 s at 512, 0.58 s at 1,024, 2.0 s at 2,048, 5.3 s at 4,096, 14.0 s at 8,192, and at 16,384 it burns 63 s of wall and 459 s of user time before failing. That is the reported bug — `-t 1000` spending 19.7 s on a two-file library, `-t 20000` failing inside rayon's `build_global` with EAGAIN against this machine's `RLIMIT_NPROC` of 22,609 and then surviving a first SIGTERM.

**So `MAX_THREAD_OVERSUBSCRIPTION = 4` sits in a wide gap rather than on a tuned point**, and the gap is left wide on purpose: the case that justifies any oversubscription at all is the one that cannot be measured here — videos on a network mount or a slow disk, where workers block on I/O and cores idle. A ceiling tuned to local decode would say 1 and refuse it. `MIN_THREAD_CEILING = 16` is a portability floor for the same reason, and does nothing at 4 cores or more: on a one-core VM the useful worker count is set by the storage's latency and has nothing to do with the CPU, where 4x would land at 4. Per core rather than flat so it travels — a flat 32 is a hard cap on a 128-core machine and 16x oversubscription on a dual-core one — and per core also tracks the memory, since the machines with many cores are the ones with the RAM for many frame buffers.

**It is bounded in `main` rather than in `run`, and clamped rather than refused.** Early because rayon's `build_global` allocates the whole pool eagerly, so an absurd value is already spent by the time `run` — where every other numeric flag is validated — is reached. Clamped because `-d`, `-p` and `--min-duration` change what the run *reports* while a thread count changes only how fast the same answer arrives, which is the same claim that keeps the count out of the cache `Stamp` and that `test_threaded_decode_is_bit_identical` holds up over the whole corpus. `active_threads` is the clamped figure everywhere after that — the rayon pool, `ThreadBudget`, the worker count and the `Settings ->` line all read it — so nothing downstream ever sees the number the user typed, and the clamp is said out loud (`log::warn!`, named in terms of memory) rather than applied silently.

**Labels are resolved globally, not per group** (`export.rs` pass 1). Precedence is REVIEW > DELETE > KEEP: a file marked DELETE in any group reads DELETE in every group it appears in — including one where it won the ranking — and a file held for REVIEW anywhere is held everywhere. The consequence is that deletions chain: B loses to A in one group, C loses to B in another, and a single pass removes both while A survives, though C was never measured against A. Each hop is a direct measurement; the end-to-end conclusion is their sum. That is deliberate — it is what stops a chain needing one re-run per hop — and it is why a group can end with no survivor at all (7 of the 129 groups a default scan of the local corpus produces, holding 19 files; every one of them traces to a survivor in another group, verified against `benchmark/labels.csv`, and three — `barbell biceps curl_{36,38,39}` — take two hops to get there rather than one).

Bit-derived metrics (quality, size) are compared **only within a codec** — a mixed-codec group ends with one survivor per codec, all flagged REVIEW. Both rules are load-bearing safety properties described in the README's Safety section.

**The `-p` gate reads `max(coverage_a, coverage_b)`, and the DELETE rule deliberately does not re-read it.** This is by design, not an oversight, and it is what makes clip detection work: a two-minute clip cut from a twenty-two minute episode covers ~100% of the clip and ~9% of the episode, so only the clip's side can ever clear a threshold. The pair is admitted if *either* file is sufficiently covered, and `export.rs` then asks only whether a measurement exists for the pair (`matches.coverage(idx, s).is_some()`), never how large it was.

**Zero coverage is refused separately from the gate, because `-p 0` cannot refuse it.** `measure_pair` tests `pct_a.max(pct_b) <= 0.0` before it tests the floor. Without that, `-p 0` made `< min_match_percent` false for every pair phase 2 was handed, and on the direct route phase 2 is handed *every pair in the library*: `-d 4 -p 0` over 110 unrelated generated files reported one group of 110 — 109 DELETE, `0.00` matched seconds on every row — where `-d 0 -p 0` over the same files reported none, because it took the index route instead. That put `index_is_cheaper`, a pure performance heuristic, in charge of a correctness question, and reached the exact state the `-d` cap at chance exists to prevent (one group, one survivor) through the flag nobody had bounded from below. The index route was quietly wrong at `-p 0` too, just less visibly — a proposed pair need not survive phase 2, so a scan of the local corpus at `-d 4 -p 0` reported 95 rows with `0.00` matched seconds; it now reports none, and the two routes agree at every `-p` as they are documented to. `-p 20` is byte-identical either side of the fix. The test is written as a separate `<= 0.0` rather than by turning the gate into `<=`, because `-p 100` must keep admitting a fully covered pair.

The consequence worth knowing before touching this: the file with the LOW coverage is normally the host, the host is the longer file, and length is the first ranking metric — so in a genuine clip/host pair the low-coverage file wins KEEP by construction and is never the one deleted. That protection is incidental rather than enforced. When the two coverages differ for some other reason (one file having several samples that all match a single sample of the other — a repeated or near-static frame — rather than one file containing the other) and the durations sit inside `DURATION_TOLERANCE_SECS`, length cannot separate them, the ranking falls through to size, and the low-coverage file can be the one marked DELETE. Still reachable at default settings, though the corroboration rule thinned it out a great deal: 3 of the 235 DELETE rows a default `-d 4 -p 20` scan of the local corpus produces (181 distinct files, some of them deleted in more than one group) share under 20% of their own runtime with a file their group keeps, against 11 of 167 before it. The pair to look at now is `archive/lat pulldown/lat pulldown_{21,22}.mp4` — 2.00 s and 2.40 s, `_21` marked DELETE having matched 0.07 s of its own 2.00 s. The example this paragraph used to name, `lat pulldown_{7,15}.mp4`, is no longer one: corroboration took that pair from 0.17 s / 1.14 s shared to 4.04 s / 5.00 s, which is what a genuine duplicate looks like. Report-only by default, and the report prints each row's own matched seconds next to it, so the information is in front of the user. Do not "fix" this by gating DELETE on the deleted file's own coverage without first working out what that does to clip detection.

**The length-protects-the-host argument has a second hole, and a single keyframe is enough to open it.** A file whose container holds one keyframe produces one hash, and `sample_times` gives the last sample an end of `total_ms` — so that lone hash stands for the entire runtime and the file's coverage is binary: 0% if nothing matched, 100% if anything did. No `-p` can gate it, because `max(cov_a, cov_b)` clears on its side alone. `archive/leg raises/leg raises_19.mp4` is 8.84 s with one keyframe; at `-d 10 -p 90` its hash landed within tolerance of 3 of the 10 keyframes in `leg raises_18.mp4`, giving 100% against 31.2%, and `_18` was marked DELETE despite 4.1 s of it having no match and being the higher-quality encode (237.8 vs 120.2 kb/f). Here the low-coverage file was the SHORTER one, so length ranked it *below* the file that was fully covered rather than protecting it.

**The third hole is a runtime nothing could measure, and it inverted the ranking outright rather than merely failing to protect.** `fingerprint::duration_seconds` returns 0.0 for "the container never said", and `GroupMaxima::tier(Length)` read that as a length: `0 >= max - DURATION_TOLERANCE_SECS` is false whatever the group holds, so such a file lost the FIRST metric compared, against every other member, always. It then lost the quality tier for the same missing number, since `bitrate` divides by it. `Priority::Quality` had carried an explicit guard for an unreported frame rate since the beginning ("no claim either way, not the worst copy here"); length had none. Demonstrated with a 20 s raw H.264 elementary stream holding a 10 s MP4 of the same footage: the host was marked **DELETE** against the clip cut out of it, on a row reading `00:00:00`, `0bps`, `-` quality and `0s matched` — because `matched_seconds` is `coverage × duration` too. Reachable from raw elementary streams above all (`-x` is what walks to them), truncated downloads, and any container libavformat cannot get a runtime out of.

Both halves of the fix matter and they are in different modules. `utils` treats an unmeasured metric as unknown in BOTH passes — `tier` returns 1 and `GroupMaxima::compare` returns `Equal` — because the tiers saying "no claim" and the raw value pass then reading 0 against ten thousand milliseconds is the same condemnation one pass later; `utils::measurable` is the single definition (length needs a duration, quality needs a duration and a frame rate, resolution and size are always known). That alone is not enough, and the reason is worth keeping: with length and quality tying, SIZE decides, and size is no substitute for length — a five-minute clip at a high bitrate is comfortably larger than the two-hour capture it came from, so the fall-through marks the host for deletion just as surely as the zero did. So `export.rs` treats an unmeasurable runtime as an INCOMPARABLE class, exactly like a foreign codec: every unmeasured file is held REVIEW, the measured files elect a champion of their own to be held beside it (deferring to the group's pick when the pick is one of them, the same deferral the codec standoff makes for the same reason), and the measured also-rans are deleted as before, because they lost to a file they really were measured against.

Not fixed by measuring the runtime from the samples, which is what `clock_restarted` does one line away in `fingerprint_video` and what the reported diagnosis suggested. `sample_times` only has a real clock to work from when the packets carried one, and the files this is about carry none at all: a raw H.264 stream's packets have no dts and no pts, so the samples fall back to one nominal millisecond each and reading that back would invent a hundredth of a second plus the enormous bitrate that follows from dividing a file by it. FFmpeg's own tools report N/A for these files. Extending the correction to `duration_sec <= 0.0` would also have cost a `CACHE_TABLE` rename — a stored field changing value — and every user a re-decode of their whole library, for a class of file no test here could produce: a container with per-packet timestamps but no duration. MP4, Matroska, MPEG-TS, MPEG-PS, FLV and Ogg all report a runtime, including truncated and fragmented ones. The ranking fix needs no rename and covers every route to a zero, whatever produced it.

**The comparator that decides all of that has to be a total order, and "unmeasurable" is what stopped it being one.** `find_best` hands its relation to `max_by`, which folds left and keeps whichever element the fold happened to land on — so a cycle in the relation makes the survivor of a duplicate group a function of the order the group arrived in. The tier pass has always been safe (`tier` is a function of one file, so a lexicographic walk over tiers composes), and the value pass one line later was not: it answered `Ordering::Equal` whenever EITHER file was unmeasurable on the metric. That equality says nothing about the two files, so it does not compose. A metric skipped for one pair is still decided for the next, the walk then reaches a LATER metric for some pairs and not for others, and that is all a cycle needs.

Three copies of one 10 s 640x480 clip reach it: `a` (av1, 42,807 B, 33 fps) beats `b` (av1, 43,451 B, 34 fps) on quality, which is where their comparison stops; `c` (hevc, 87,955 B, **no frame rate**) has no quality to compare, so both of its comparisons fall through to size, where it is the biggest file of its own codec. `a > b > c > a`. The six orderings of that group kept three different files and deleted two — `b` four times and `a` twice — a different video destroyed, on nothing a user could see, since renaming a file is enough to reorder a group. Group members are path-sorted, so a given library is still reproducible run to run; what breaks is the property `export.rs`'s DELETE rule rests on (the KEEP pick can be a file that lost a direct comparison to a file the same run marks DELETE) and the promise that the last-resort tiebreak is alphabetical.

The fix is to make the value pass a per-file key, which composes by construction. Every metric now scores a file as a FRACTION of the best value that metric can be measured against for it (`GroupMaxima::score` over `metric_max`) — the group's best for length and resolution, the best of the file's own codec for the two bit counts — and **a metric nobody could measure scores 1, level with the best**, which is the same "no claim either way" the tier pass makes one step earlier. A maximum of 0 is that statement about the whole comparison set and everyone in it scores 1, exactly how `within` already treated it. Length and resolution give every file in the group the same denominator, so measured files compare exactly as they did; the codec-relative pair keep the cross-multiplication they already had. `GroupMaxima::rank` is the whole relation in one place so a test can hold it: `test_the_ranking_is_a_total_order` walks 3,000 pseudo-random groups built to contain unmeasurable files and asserts antisymmetry and transitivity of both `Greater` and `Equal` over every triple, and `test_which_copy_is_deleted_does_not_depend_on_the_order_the_group_arrives_in` runs all six orderings of the case above armed.

The unknown has to land somewhere definite, and the direction matters: reading the unmeasured value as a zero is the bottom, which is the inversion the `tier` guards above document at length. Dropping the metric from the whole group when any member is unmeasurable on it also restores transitivity, and it was refused — it throws away the length comparison between two files that WERE measured whenever a third was not, and length is the metric that keeps a long file safe from the clip cut out of it. Reports are byte-identical on the local corpus at `-d 4, 8, 12, 16` and `20`, and all three accuracy profiles pass unchanged: no file there has an unmeasured length or frame rate, which is the argument FOR fixing it rather than against.

Two smaller consequences. The report prints `-` for the length and leaves `length_seconds` blank (`null` in JSON), the sentinel the frame rate and quality columns already used: a zero-length video and a video of unknown length are different findings, and a row reading `00:00:00` beside 20 samples looks like a malfunction. And a library made entirely of such files now deletes nothing at all, which is the honest answer — the safety rule the DELETE label rests on is a length comparison, and there is no length to compare.

**The corroboration rule closes that specific case and does not close the shape of it.** A witness has to be a different sample on *both* sides, so a one-hash file can never reach the loose tolerance and is held to `strict` — 8 bits at `-d 10`, where `_19`'s match sat at 10. That pair is gone from the `-d 10 -p 90` run and the genuine `_8`/`_10`/`_11`/`_15` cluster is untouched. What has not changed is the arithmetic underneath: a one-hash file that *does* match strictly still reads 0% or 100% and nothing gates it. The remaining levers are the same ones — a tighter `-d`, or a `--min-duration` floor. `--keyframe-interval` still cannot help: it only thins keyframes and never adds them.

**The extension list is a guess, and its two failure modes cost very different amounts.** `DEFAULT_EXTENSIONS` in `main.rs` is what a folder *walk* assumes a video is called — a named path is never filtered, per the `sources` module doc. An extension too many costs one file the decoder rejects, named in the run's problem list; an extension too few costs a folder that prints "No videos found" and a user who concludes the tool is broken. So the list runs to 18 containers rather than the original 6, and `.ts` is in it despite being how a TypeScript tree names every file: it is also how every DVB capture and half the camcorders on earth name their footage, and the failure it causes is loud and localised while the failure it prevents is silent.

**`-x '*'` is not a wider list, it is the absence of one, and no list could replace it.** A file with no extension has nothing for `Path::extension` to return, so no entry could ever name it — which made a DVD rip, a camera dump, or anything named by a content hash unreachable from a walk. `sources::Wanted` is therefore three shapes (`Anything`, `AnythingBut`, `OneOf`) rather than a set, the wildcard wins over anything written beside it, and `-x '*.mkv'` is normalized to `mkv` because a shell user writes it that way and the alternative is a suffix that silently matches nothing. Under `Anything` the extension filter no longer turns directories away, so `walk_folder` checks `entry.file_type().is_dir()` first — WalkDir already knows, so it also saves a stat per folder in every other mode.

**An entry prefixed with `!` is a subtraction from that list, not a second kind of request, which is why it needed no flag of its own.** `normalize_extensions` reads the list left to right into two sets and then answers one question: the base is `Anything` when `*` is written or when nothing positive is (`-x '!flac'` can only mean "everything but"), and the exceptions come off it — `AnythingBut` if any survive, `Anything` if none do. A positive list with an exception beside it is just that list minus the exception (`-x 'mp4,mkv,!mkv'`), so there is no precedence rule to learn and no ordering between two flags to get wrong. Both ways of writing the empty walk are refused rather than walked (`-x '!*'`, `-x 'mkv,!mkv'`): a scan that cannot match a file is a typo, and "No videos found" is how a user concludes the tool is broken. `AnythingBut` accepts a file with no extension for the same reason `Anything` does — nothing named it — and it counts as `any_extension` (`Wanted::is_a_guess_at_video`), because excepting one suffix turns nothing away for *being named wrong* and the run must not call what it found "video files".

The case it exists for is audio: FFmpeg fingerprints a `.flac` with embedded cover art as a one-frame mjpeg video carrying the track's full runtime, so `--min-duration` cannot reach it, `-p` cannot gate a single sample (see the single-keyframe invariant), and a music folder scanned under `-x '*'` groups whole albums by their artwork. A narrower positive list is not the answer there, because the same folders are the ones holding files with no extension at all.

It is also the one mode in which the run must not call what it found "video files", which is what `Library::any_extension` is for: every other setting has already turned away anything not named like a video, while this one hands the decoder whatever is there. A scan of a home directory announced "Found 229112 video files" and then spent the run failing to decode 229 thousand of them. The same correction applies to `fingerprint_failed`'s summary label, which is now "file(s) could not be fingerprinted" — that bucket holds precisely the things that turned out not to be video.

**A filename that is not valid UTF-8 is skipped where it is found, not mangled into a path that does not exist.** Every path downstream of `sources` is a `String` — cache key, report column, deletion target — so `ScannedFile::of` returns `Option<Self>` and the two callers record `unreadable` with "filename is not valid UTF-8". It used to go through `to_string_lossy`, which queued the file under a name with U+FFFD where the bad byte was and produced `Failed to process .../bad<U+FFFD> name.mp4: No such file or directory` — a missing-file error against a file the walk had just listed, blaming the decoder for a rename this tool had done itself. `read_path_list` has always handled a piped-in line this way; the walk simply did not. Never a safety problem (a lossy path cannot be opened, so it cannot be fingerprinted, so it cannot become a DELETE candidate) and it was already loud and exit 2 — what changed is which thing gets blamed. Decodability is settled **before** the inode is claimed, so an unusable name cannot stand in for a hard link that has a usable one, which would lose both.

**One report body is built per run, and which one is decided before the loop.** `wants_txt` / `wants_csv` / `wants_json` in `output_results` gate the three bodies; the text line is built when *either* the console listing or a `.txt` report will read it, and pushed only for the latter. Only the JSON tree was gated before, which was the cheap half: the text body is the whole listing accumulated in a `String` and the CSV is the whole listing again through a serializer, so a JSON run built both and a run with **no `--output` at all** still built both. Measured on the local corpus at `-d 18` (9,003 groups, a 31 MB CSV and a 17 MB txt), peak RSS: report-only run 66 → 18 MB, `-o x.csv` 67 → 50 MB, `-o x.json` 3.24 → 3.19 GB, where the per-link tree dominated and the gating barely moved it. The gate still decides which body is built; what has changed since is that no body is held at all — see the streaming invariant below. Wall time is unchanged to within noise, and all three formats are byte-identical either side. `test_each_format_still_carries_its_whole_body_now_that_only_one_is_built` is the guard, because the saving itself is invisible from outside and the failure it risks is an empty report.

**The report is streamed as the reporting pass produces it, so no format holds its own body.** The JSON is what forced it and it was the one place the flat-memory discipline came apart: `serde_json::Value` is an `IndexMap` per file and another per link, and a group of `g` members contributes `g * (g - 1)` links, so the tree ran roughly seven times the document it rendered to and `to_string_pretty(...).into_bytes()` then made a second whole copy of that document beside it. The other two were each one copy of their own document — and the text body was two, since the summary was appended by building a second `String` out of the first. Measured at `-d 18 -p 20` on the local corpus (9,003 groups; a 288 MB JSON, a 23 MB CSV, a 12.8 MB txt), interleaved three runs each:

| `--output` | wall | peak RSS |
|---|---|---|
| `rep.json` | 8.0-11.3 s → **5.1-5.3 s** | 2.25 GB → **20-21 MB** |
| `rep.csv` | 1.0 s → 0.9-1.1 s | 41-42 MB → **19-20 MB** |
| `rep.txt` | 0.9-1.0 s → 0.9 s | 43-44 MB → **19-20 MB** |
| none | 0.9 s | 19 MB |

Every format now sits on the report-only floor: the body contributes nothing measurable to peak RSS whatever its size. Only the JSON gains time, because it was the only one paying for a structure rather than for its own bytes. All three are byte-identical to what the whole-document writers produced, on a file, on stdout, through a FIFO, through a symlink and into a read-only folder.

`ReportStream` is what holds the destination open across the pass, and it can be opened *before* the pass only because nothing in a report's opening depends on it — which is a real constraint for the JSON, whose summary leads the document, and is why that summary object moved out of the writing block and up to where the sink is constructed. Every figure in it was settled by the disposal pass above. Three destinations, and they are not interchangeable: a file gets the scratch copy `write_file_atomically` would have made, held open and renamed over the report at the end (`Scratch::beside` / `Scratch::commit` are that function's two halves, now shared rather than copied); `-o -` streams straight down the pipe, which is safe because nothing else in a run writes there and `console_for` has already decided what stderr says beside it; and a destination a rename must not replace — a FIFO, a symlink, a device, or a read-only folder that will not take a scratch file — falls back to holding the document and handing it to `write_report`, keeping exactly the write it had. **That fallback is the one thing streaming gives up**: for those destinations the report is still one `fs::write` after the run is over, so a run killed mid-pass leaves the previous report standing, and for a streamed one it does not. The scratch copy is what makes that acceptable everywhere else — a killed run leaves the old report whole and the half-written copy under a name nothing reads.

**`ReportStream`'s `Write` impl records the first failure and reports every write as done, and that is the load-bearing part rather than a shortcut.** A report that could not be saved is a problem this run REPORTS — logged, tallied, exit 2 — and never one it returns, because by the time a body is being written the disposal pass has already run and propagating an error out of `output_results` throws away `deleted_paths` on the way, leaving the cache claiming fingerprints for files this run has just removed. That was free while the bodies were a `Vec` and a `String`, which cannot fail; the `?` on a `csv::Writer` record now sits over a real file, so the sink has to be the thing that swallows. `finish` answers for the first failure in the same words the whole-document write used, and everything after it is skipped rather than retried — nothing that stops one group finishes the next.

The JSON layout is reproduced by hand, so it is pinned by hand. `write_nested` renders one value with `to_string_pretty` and pushes every line out by the depth that value sits at, which keeps serde_json the authority on what pretty JSON looks like rather than reimplementing its `Formatter`; a variant that did the same indenting in one `str::replace` per group measured 4.90-5.03 s against 5.03-5.05 s, so the remaining time is serde_json's rendering and not the walk. `test_the_streamed_json_is_laid_out_exactly_as_one_rendered_whole` parses the finished report back — `preserve_order` returns the keys in the order they went in — and demands the file equal `to_string_pretty` of that, which catches the indent, the depth of each piece, the comma between groups and the brackets around them, and it covers the empty document too, since `results` is written closed rather than opened and closed. `test_a_streamed_report_replaces_the_last_one_and_leaves_no_litter` re-asks the atomic writer's promises — one-step replace, permissions kept, no litter, a symlink written through — of the sink that no longer calls it, for all three formats.

**Where the report goes and how it is written are one decision, taken before any work starts.** `main::report_target_for` turns `--output` and `--format` into a `ReportTarget` (a `Sink` and a `Format`), which is also where the path check that used to be `check_output_path` lives, now including whether the destination can actually be written (`ensure_writable`) — the report is the LAST statement of `output_results`, after the disposal pass, so `-o ro/rep.csv --delete --permanent` into an unwritable folder removed the file and then lost the only record of which one it was. The probe is one `create_new` (removed again immediately, so an interrupted run still leaves no empty report behind) falling back to a non-truncating open when the file is already there, which is also why a read-only FOLDER holding a writable report is still allowed. A target that is not a regular file is accepted unexamined, because opening a FIFO to ask would block and then consume its reader; `export.rs` no longer parses a path to decide anything, and the extension is consulted in exactly one place (`format_from_extension`) and only when `--format` is silent. Three things fall out of that. `-o -` is stdout rather than a file named `-`, which it used to create — the parent of `-` is the working directory, so the check passed — and it works only because nothing else in a scan writes there: every result line, both progress bars and the confirmation prompt are on stderr. `./-` still names the file. A report on stdout also REPLACES the console listing rather than joining it (`console_for`): the two are the same run said twice, so `-o -` used to print everything to a terminal twice over, and a pipe still scrolled the whole listing past the user on the way to the line they grepped for. The summary is the exception, because a `.txt` report is exactly that listing plus that summary and the JSON carries the same figures under `summary`, while the CSV carries neither — so stderr keeps the receipt only for CSV. A report written to a FILE keeps both, because then the terminal is the only place the run is visible while it happens. Moving the listing to stdout by DEFAULT (so `vid-fp DIR | grep DELETE` needs no flag) was considered and refused: the listing and the summary are one document, so the summary would have to follow it and `vid-fp DIR --delete > /dev/null` would discard the receipt for a destructive run, or stay behind and leave `vid-fp DIR > report.txt` no longer holding the txt report. It would also make the aligned human table, the one output format with no stability promise, the surface pipelines get built on. `-o -` is the opt-in and stdout stays empty otherwise. `--format` with no `-o` is refused rather than read as "and put it on stdout", because turning a run that writes no report into one that does is not a default worth guessing at. And a broken pipe on stdout (`-o - | head`) is swallowed in `write_report` rather than recorded as `report_write_failed`: a reader closing early is how a pipeline ends, not a run that did less than it was asked. Every other write failure is still a problem and still exit 2.

**The report replaces the last one in one step.** `fs::write` truncates in place, and the report is the LAST statement of `output_results`, after the disposal pass -- so a run killed mid-write destroyed the previous report and left a truncated one where it was, which is exactly the file `--from-report` hands back: a plan for a library that has already been acted on, minus whatever rows did not reach the disk. It degrades safely rather than dangerously (a half-written row loses `size_bytes` and the replay refuses it as CHANGED), but "the last rows are missing" is a plan that silently keeps files it condemned. `write_file_atomically` writes a scratch copy beside the report, fsyncs it, and renames over the top; `Scratch` removes it on any early return, in the same shape and for the same reason as `Conjured`. Two carve-outs keep the behaviour above intact, and both are named at the site: a scratch file that cannot be CREATED falls back to the write it replaced, because `ensure_writable` deliberately allows a read-only FOLDER holding a writable report and a rename cannot make a file in one; and a destination that is not a regular file is written through rather than replaced (`replaceable_by_rename`), because a FIFO's reader would wait for ever on a pipe that had been renamed away and a symlinked report is one kept somewhere else under a local name. A failure AFTER the scratch file exists is returned rather than fallen back on -- whatever stopped the copy would stop the in-place write too, having truncated the old report first. The file's permissions are carried over before the rename, so a report the user had narrowed does not widen back to the default. A run killed outright leaves the scratch copy behind, since no destructor runs; the report it was replacing is still whole, which is the half that matters.

**A run that completes writes its report, including when it has nothing to compare.** The two endings that never reach the comparison — `video_files.is_empty()` and `fingerprints.len() < 2` — used to return before `export::output_results`, so `--output` was silently not written and the run exited 0. The file it names is then an EARLIER run's report, and the documented workflow hands exactly that file back to `--from-report --delete`: a second scan that comes up short (an unmounted share, a `--min-duration` that swallowed the lot, an `--extensions` list that no longer matches) replayed a plan for a library that is no longer there. `dispose_one`'s size check spares only files whose bytes moved, so an unchanged file that no longer has a duplicate beside it is removed against a measurement nothing in that run made — including the last copy of it: run 1 marks `b` DELETE against `a`, `a` is moved away, run 2 sees one file and says nothing, and the replay takes `b`. Both endings now go through `main::conclude_without_comparing`, which asks `output_results` for a run with no groups rather than assembling an empty report of its own — that is what keeps the three formats' empty bodies the same shape as their full ones (a scan of two unrelated videos has always written exactly this: a header-only CSV, `"results": []`, a summary reading zero) and what makes the overwrite visible, since the "Results saved to" line comes from the same place. An interrupted run still writes nothing and says so with exit 130.

A scan that fell SHORT writes its empty report too, which is the opposite of what `prune_obstacle` decides about the same run and is deliberate. The trades are not comparable: a prune against an incomplete scan discards hours of decode, an emptied report costs a second scan against a warm cache. And the report has a failure mode the cache does not — leaving it alone stands a deletion plan in front of a user as though this run had endorsed it. `-o` says where this run writes, a successful scan overwrites the same file, and the overwrite is announced on a run already exiting 2 and saying why.

**Nothing is destructive without `Disposal`.** `export.rs` cannot touch a file unless `main::disposal_for` constructed one from `--delete` / `--permanent` / `--move-to`. `--from-report` is no exception: it bails with an explanation rather than reading a report it could not act on.

**The `--move-to` loop guard asks about the REQUEST, not about what the request found.** `sources::collect` returns a `Library` — the files, plus the folders that were walked and the `--exclude` paths that resolved — and `Library::walk_reaches` answers "would a scan of this same request find a file moved to `dest`". It used to be asked of the parents of the found files, which is the same question only in a flat library: `vid-fp lib -r --move-to lib/dupes` over a tree whose videos all live in `lib/sub` proposed no parent that enclosed `lib/dupes`, so it sailed through, and the NEXT run re-ingested what it had moved, kept that copy and moved the original in beside it — two runs to empty a library into `dupes/`. Putting the destination one level deeper (`lib/sub/dupes`) was caught, which is what made it easy to miss. A folder is a scan root by having been pointed at, not by having yielded anything: one that is empty today is one a moved file is found in tomorrow. Excludes are honoured because the refusal's own advice is to exclude the destination, and under the parent-based check that advice did not work — the root still enclosed `dest` whatever `-e` said. Nothing else earns an exemption, including a non-recursive walk: the landing paths sit at least two levels under `dest` so today's run would not reach them, but the destination is still inside the library and one `-r` later it is the same loop.

**A run refused by that guard takes back the destination it made.** The folder has to exist before anything can be decided about it — `canonicalize` needs a real inode, and `resolve_excludes` canonicalizes too, so the refusal's own advice (`-e <dest>`) would not resolve on a destination that is not there yet — and every check that can refuse the run comes after `resolve_move_to`. So `vid-fp lib -r --move-to lib/dupes` bailed correctly and left an empty `lib/dupes` INSIDE the scan root: a directory made by a run that did nothing, which the user has to clean up before their library stops containing it, and which the same command hits again the next time. `resolve_move_to` therefore returns a `Conjured` beside the path — the directories `create_dir_all` had to make, read off the filesystem BEFORE the creation because afterwards nothing distinguishes them from what was already there — and its `Drop` removes them unless `keep` has been called. `keep` sits after the containment checks in `run` and after `report::apply` in `--from-report`, so every start-up refusal in between is covered too: an `--output` that cannot be written, a scan path that will not resolve, a report that cannot be read. Undoing is `remove_dir` deepest-first, never `remove_dir_all`, which is what makes it safe to fire on any early return — a destination that is not empty is not this run's to remove, including one holding files it has already moved.

**A symlink is a scan root too, and both halves of that guard had the same hole.** `--exclude` and `walk_reaches` are two questions about the same thing — which bytes this request reaches — and both compared the path the WALK spelled against a canonical path. Under `--follow-symlinks` those never share a component, so both silently answered no. `-e keep` did not protect `keep/precious.mp4` from a run that reached it as `scan/linkdir/precious.mp4`, and `remove_file` on that walk path unlinks the real file: `--delete --permanent` destroyed exactly what the flag was written to save. It failed in both directions, which is what made it unworkable-around — excluding the link path the user can actually see in the report is canonicalized into the real folder and matched nothing either. `sources::is_excluded_target` is the fix, and it is one function for both directions because canonicalizing the walk path makes them the same comparison. It is asked only of an entry that IS a link, or of any entry when links are being followed, so the default path pays nothing; directories are canonicalized in `filter_entry` (few, and it buys pruning of an excluded subtree) and files only after the extension filter has thinned them.

The loop guard needed the other half of it: `walked` now records the canonical TARGET of every directory symlink the walk descends through, not just the roots the user typed. `lib/link -> store` puts every file in `store` inside the scan while `store` is under no typed root, so `--move-to store` sailed through and the next run found its own output under `lib/link/...` and moved it a level deeper — the exact loop, reached by the one route the guard could not see. `Reached` carries the link beside the target because the message otherwise read "store is inside store, which this run scans": true, and silent about the one path the user has to go and look at.

The benign-looking variant is why none of this is gated on `--follow-symlinks`. A symlinked FILE is walked by default (the stat follows it), so it escaped `-e` too; `remove_file` then unlinked only the link, the target survived, and the run reported the target's bytes as freed having freed none of them.

**A removal that took a name rather than the data is not space freed, and only the stat before the unlink can tell.** `sources::collect` deduplicates on (device, inode), so no two names for one set of bytes ever both reach a DELETE decision — which is exactly why the case that matters is the one it cannot see: the other name is OUTSIDE the run. `scan/dupe.mp4` hard-linked to an unscanned `store/dupe.mp4` was unlinked, counted at its full size, and reported as "1.3MB freed" against a `store/dupe.mp4` that still held every byte. A symlink is the same claim with a worse aftertaste — the walk stats through it, so it enters the library carrying the target's size and codec, `remove_file` then takes the link, and the video survives at a path this run never printed, so a re-run reports a clean library. `export::on_disk` answers both questions out of the `symlink_metadata` the staleness check was already taking (`file_type().is_symlink()`, `nlink() > 1`), `Fate::Done` carries the answer, and both callers add the bytes only when they went away. The row is labelled **UNLINKED** rather than DELETED/MOVED — a word that had to be added to `report.rs`'s `KNOWN_ACTIONS`, since replaying such a report must be the no-op every other past-tense action is, and that row's file is the one that is still readable. It is not a problem and not a skip: the user asked for that path to go and it went, so nothing about the exit code moves; what would otherwise be unaccountable is the byte total, hence `aliased_line` (which carries the missing bytes as well as the count, because a `--move-to` run of nothing else reads "Moved 1 file(s) (0B total)") and the JSON's `files_unlinked`/`bytes_unlinked`. A symlink needs a second stat for the size, because `symlink_metadata` on a link reports the length of the link text and every symlinked file would read as CHANGED — the direction that quietly stops deleting anything. The dry run's `reclaimable_bytes` is deliberately left as an upper bound: knowing better means stat'ing every candidate, and a run that removes nothing promises nothing.

**Which files that is true of depends on the MODE, and the two kinds of alias point opposite ways once it is not `--permanent`.** `frees_nothing` is the whole rule and it is not "every alias": rename(2) moves an inode, so a hard link relocated by `--move-to` or by the trash arrives at the destination holding every byte of the video — the destination has the file, the sibling name still has the file, and nothing anywhere was unlinked. A symlink renamed the same way arrives as a pointer, and the footage is still at a path this run never printed. Reading `nlink > 1` as an alias in every mode charged `--move-to` twice for the first case: the row read UNLINKED, a word that says the data stayed put, and its bytes were struck out of the figure beside it, so a run that relocated nothing but hard links reported "Moved 3 file(s) (0B total) under /dupes" over a destination holding three complete videos. So `Alias` is three-valued (`None`, `HardLink`, `Symlink`) and `dispose_one` — which already has the `Disposal` — decides from both: any alias falsifies `--permanent`'s promise that the bytes are gone, and only the symlink falsifies trash's and `--move-to`'s promise that the file is somewhere else instead. `Fate::Done { aliased }` keeps its shape, so both callers and the `--from-report` path are unchanged. The one case it still under-claims is a symlink moved ACROSS filesystems, where `copy_then_unlink`'s `fs::copy` follows the link and the destination does get a real copy; the direction of that error is the safe one (bytes not counted rather than bytes falsely claimed) and telling it apart would mean `move_under` reporting which branch it took. `test_a_rename_carries_a_hard_link_with_it_and_leaves_a_symlink_behind` drives both arms of one `--move-to` run.

**The action column is `export::ACTION_COLUMN`, and it is a constant because it has drifted.** Both listings — `export.rs`'s results table and `report.rs`'s replay — pad the leading action to a fixed width so it forms a column the eye can run down. It was a literal `8` in two format strings, which held for as long as DELETED/CHANGED/SKIPPED were the longest words; adding UNLINKED (nine characters with its comma) shifted every field of exactly those rows one place right, and those are the rows a reader is most likely to be studying, since they are the ones whose byte total does not add up. `KNOWN_ACTIONS` is the complete set of words either listing can print — a replay has to recognise every word this tool writes — so `test_the_action_column_is_exactly_wide_enough_for_the_longest_action` derives the width from it and asserts equality, which catches a column left too narrow AND one left needlessly wide.

**`export::dispose_one` is the only copy of the destructive step**, and it takes a path and the size that file was measured at — nothing else. That narrowness is what made `--from-report` cheap, and it is worth preserving: widening it to need a `VideoFingerprint` again would mean the report mode either re-fingerprints or grows a second, weaker version of the staleness check. Both callers pass a size from the same moment the delete decision was made (the scan; the report's `size_bytes` column), and a file that no longer matches it is reported CHANGED and left alone. `fingerprint_video` therefore takes `file_size` as an argument rather than re-stat'ing: the fingerprint's size and its stamp's size are then one measurement from one moment, and a file that grew between the scan and its own decode reads as CHANGED instead of being deleted against a figure nothing else in the run agreed with.

**`report.rs` trims every cell it reads except the path.** Leading and trailing spaces are legal in a filename and both writers emit them verbatim, so trimming `full_path` meant the tool could not replay its own report — it looked up a *different* path, and the size check is taken against whatever survived the trim, so a same-sized neighbour was deleted instead. A whitespace-only cell is still treated as empty.

**A report's DELETE rows are the user's decision, not the tool's.** The safety rules below (direct measurement, one survivor per codec, a ranking that only condemns a file against a copy it was measured against) are enforced by the run that *writes* a report. `report.rs` deliberately re-imposes none of them — a group may be emptied completely, which the writing run can now do on its own too — because the file has been edited by then and second-guessing it would defeat the point, which is adjudicating REVIEW rows. What it does keep is the confirmation prompt, the size check, and a hard rule that an action word it doesn't recognise is never guessed at: the file is left alone and `stats.report_unusable` fails the run. **A path that is not the canonical one this tool writes is refused by that same rule** (`not_canonical`), and it is a safety property rather than tidiness: every scanned path is absolute with no `..` in it, so anything else arrived by hand. A relative path is resolved against the working directory, so one report acts on different files depending on where it is replayed from — and `move_under` strips the leading `/` and JOINS, so a `..` survives that arithmetic and comes out the other side. `../../outside/clip.mp4` landed at `/tmp/outside/clip.mp4` from a `--move-to /tmp/x/dest` run, creating the directory on the way and leaving `dest` empty: the documented "undo the whole run with one copy back from the destination" defeated, and `Conjured` knowing nothing about it. `--permanent` reaches the same file by the same arithmetic with nothing to undo. `Component::CurDir` is deliberately NOT a fault — `/a/./b` names the same file from anywhere and mirrors to the same slot — so the rule refuses only what changes which bytes are touched. It sits in `Rows::consider` rather than in either format reader, which is what makes it true of the JSON as well. Columns are located by header name (and JSON fields by key), which is what lets the CSV layout be chosen for whoever reads it: reports written by older builds, and reports a spreadsheet handed back reordered, replay identically. What a row is *called* in a complaint is per-format on purpose — `line 14` for the CSV, `group_1 file 2` for the JSON, which is how each is actually navigated — because a complaint about a row the user cannot find is one they cannot act on.

**The confirmation sits between the two passes of `output_results`, not at start-up.** `confirm::approve` is asked once the DELETE set is resolved, because that is the first moment there is a count and a byte total to show. Declining does not abort: it rebinds `disposal` to `None` for the rest of the function, so the labels, the summary and the JSON all describe the run the filesystem actually saw. It is interactive-only (`stdin` *and* `stderr` must be terminals) so a pipeline can never block on it, `--yes` skips it, and everything that isn't an explicit yes — EOF, a read error, an interrupt, three unparseable answers — leaves the files alone.

**No error in `fingerprint.rs` names the file it is about, because every caller already does.** The messages used to, and the result was `Failed to process X: Failed to open video file: X: no demuxer recognised ...` — the same path twice on a line a `-x '*'` run can emit a quarter of a million of. The names live in `main`'s two reporting sites (and in `Refusal`'s replay), so `probe_streams` does not even take a path. One error keeps a wrapper of its own kind: `open_video` adds "Failed to open video file" to everything EXCEPT `NotMedia`, which is not a failure to open a file but a decision not to open one — and which is also the verdict replayed from the cache, where there is no open to blame and no way to add the prefix. Wrapping it made a file read one way on the run that discovered it and another on the run that remembered it; `test_a_remembered_refusal_reads_exactly_like_a_fresh_one` runs both and compares. Trimming the messages is also why `refused_ff8_probe1` was retired: `Refusal::Said` stores the sentence a run printed, so the wording is part of what is in that table.

**A failure the summary will account for is never printed while the run works.** Saying it twice is how a `-x '*'` scan buried its own results: 226,863 lines during the scan, then the same findings again in the summary, with the report the run exists to produce somewhere in between and long out of the scrollback. The routing is a log TARGET, `stats::COUNTED` — every `log::error!` whose message is also handed to `Tally::record` carries it, the `env_logger` format closure drops those from the console, and `--log-file` is written from the same closure BEFORE that decision, so the file always holds every line. Anything logged without the target is something no tally counts (a cache that would not compact) and still prints as it happens, because otherwise nothing would ever say it. `MAX_SAMPLES` moved 3 → 20 in the same breath and for the same reason: the summary is no longer a reminder of a list that scrolled past, it IS the list, so its examples are what the user reads. The elision line lost its "(see the errors above)" for the same reason — there is nothing above any more.

An earlier version of this capped the console at 20 lines instead of suppressing them, which is worse in both directions: still noisy enough to push the results out of view, and arbitrary about which twenty a user sees. Note what none of it changes: every failure is still counted, still a problem, still exit 2. Suppressing the lines was chosen over reclassifying "not media" as a skip under `-x '*'`, which was the other candidate and would have changed the exit code of a scan that did exactly what it was asked.

## Keeping the docs honest

`README.md`'s options table, the `Args` doc comments (which become the man page and `--help`), and the tuning/safety prose describe the same behaviour three times. Any flag or default that changes has to be updated in all three. Report formats are `txt`/`csv`/`json`, resolved once in `main::report_target_for` and written from the `Format` it produces.

**No column position is load-bearing, and it is worth keeping it that way.** The CSV order used to be frozen by two readers that indexed into it, so every new field was bolted onto the right-hand end regardless of what it meant, and `action` ended up five columns from the link data that justifies it. Both readers now resolve columns by header name — `report::column` and `local_accuracy_test::get_duplicate_files` — which is also what lets the golden `vd_results_*.csv` baselines beside the corpus stay useful: they were written by older builds with a different, shorter layout. Reorder the report freely; just never re-introduce an index.

**Every column in the link block answers for the row's own file.** That is what the `matched_` prefix promises, and it replaced a `shared_` block that broke the promise: `matched_seconds` used to be `overlap_seconds`, the pair's reconciled minimum, sitting beside a range that was this file's — so a row whose matched footage ran `0.00`–`8.84` reported `1.88` of it and read as a malfunction, with nothing in the row to say one of the numbers had changed subject. `MatchIndex::matched_seconds` is now `coverage × duration` for that row alone. On an honest match this changes no number, because both ends already agreed (a clip's `100% × 2min` and its host's `9% × 22min` are both two minutes); it only diverges on lopsided pairs, which is the case worth seeing. `overlap_seconds` survives with exactly one caller, `--min-duration`, and the two are no longer at risk of the drift that once had the gate taking the higher estimate and the report the lower — they answer different questions now. Coverage is taken over `duration` rather than `total_ms` so the figure stays under both the `length` column and its own envelope; `sample_times` only ever extends the runtime, so `total_ms >= duration * 1000` always.

`samples` (the fingerprint's hash count) is in the report because it is what makes that block interpretable — an envelope much wider than the footage is either a scattered match or a file too coarsely sampled to know, and only the sample count separates them. It is a property of the file, not of the link, and it still sits between `matched_with` and `matched_seconds`: it qualifies the figure it precedes, and that beat the block it belongs to. `framerate` is the sole figure carried raw-only, by request; its formatted form lives on the console line.

The three formats are one layout expressed three ways, and `export.rs` writes them from a single pass, so a field added to one is added to all three in the same place. The JSON's key order is only preserved because `serde_json` carries the `preserve_order` feature — without it serde_json's `Map` is a `BTreeMap` and the tree comes out alphabetized, which interleaves each figure's raw and formatted halves and buries `summary` under the whole results array.

The JSON is written only when the run resolves to that format (`wants_json` in `output_results`), and like the other two it is written as the reporting loop produces it rather than assembled first — it carries one object per measured link per file, which is what made holding the whole tree cost two gigabytes. See the streaming invariant above.

Releases are cut by pushing a `v*` tag — `.github/workflows/release.yml` runs `scripts/build-ffmpeg-static.sh`, builds the static binary against it, generates completions and the man page from the binary itself, and uploads a versioned copy, a stable-named copy, the extras tarball and the LGPL relink kit. The tag build now runs `cargo test --release --locked --features static-ffmpeg` between the build and the DT_NEEDED check, so the suite runs against the exact artifact that ships and against the vendored FFmpeg 8 — the feature flags have to keep matching the build step above it, or the test run replaces the static binary with a dynamic one and every check after it inspects the wrong file.

`.github/workflows/ci.yml` runs `cargo clippy --all-targets --locked -- -D warnings`, `cargo test --locked` and a `cargo check` on the declared MSRV, on every push to a branch. **It is a clean-checkout gate, not a correctness gate.** `tests/local_accuracy_test.rs` and `benchmark/` are gitignored, so a clean checkout is 25 files and CI never sees the accuracy harness at all — it proves the committed tree compiles standalone with a cold target dir and a fresh registry, which the development machine cannot prove, and it proves nothing whatever about grouping. Accuracy is still measured by hand. There is no `cargo fmt --check`, because the tree is not rustfmt-clean.

**`cargo clippy --all-targets` is clean, and three `#[allow]`s are what keep it that way.** Each carries its reasoning at the site; the short version is that all three lints are asking for a rewrite that would cost something real. `clippy::unnecessary_cast` on `AV_CODEC_FLAG2_FAST as i32` (`fingerprint.rs`) — the FFmpeg flag macros have no declared type, so bindgen infers one per `#define`, and within a single header the `AV_CODEC_FLAG_*` family lands on `c_uint` while most of `AV_CODEC_FLAG2_*` lands on `c_int`; the cast is redundant only for as long as this flag keeps its current bit. `clippy::needless_range_loop` on the variance/auto-crop scan (`fingerprint.rs`) — `y` and `x` index two flat 64×64 buffers *and* two 64-entry projections, one of which is re-walked per row. `clippy::too_many_arguments` on `output_results` — the two parameters that shared an axis are already `Policy`, and a bag for the rest would only hide which of them the destructive pass reads. Do not "fix" these by deleting the comment and taking clippy's suggestion.

Two release steps are load-bearing rather than decorative, and both guard failures that are silent in ordinary testing: one greps `DT_NEEDED` for `libav*`/`libsw*` and fails if the binary linked FFmpeg dynamically after all, the other fingerprints a generated AV1 clip. FFmpeg's built-in AV1 decoder is hwaccel-only, so a configure that quietly drops `libdav1d` yields a binary that passes every other test and cannot fingerprint a single AV1 file.

**The LGPL relink kit is a licence obligation, not an extra.** FFmpeg is LGPL 2.1+ and the link is static, so §6 requires shipping the means to relink — hence the `.a` archives, headers, build script and `RELINKING.md`. Keep `--disable-gpl --disable-nonfree` in the configure line: `vid-fp` is offered under Apache-2.0, which is incompatible with GPL-2. See `THIRD-PARTY-LICENSES.md`.
